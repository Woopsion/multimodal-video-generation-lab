2. 从 CLIP 到 VLM

CLIP 和 VLM 都处理图片和文本，但输出目标不一样。这个区别必须先讲清楚，否则后面很容易把 VLM 误解成“CLIP 加一个回答模板”。

维度 CLIP VLM 图像问答
核心输入 图片和候选文本 图片和用户问题
核心输出 相似度分数、ranking、top-k 自然语言答案
关键能力 判断哪段文本更匹配图片 根据视觉信息和问题生成解释、描述或答案
模型形态 通常是双塔：image encoder + text encoder 通常是视觉编码器 + 投影层 + LLM
Day12 要抓住 共享向量空间是前置基础 视觉特征要变成 LLM 可处理的上下文

3. VLM 基本架构

入门阶段先用一个通用范式理解 VLM：视觉编码器负责看图，投影层负责换维度和接口，LLM 负责根据上下文生成文字。不同模型会有不同细节，但这条主线最重要。

3.1 Vision encoder 细讲：ViT / CLIP vision 到底是什么

Vision encoder 可以先粗暴理解成“图片特征提取器”。它的输入是图片张量，输出不是一句话，也不是最终答案，而是一组视觉向量。后面的 projector 和 LLM 会继续使用这些视觉向量。

概念 它是什么 在 VLM 里的作用
Vision encoder 总称：任何把图片编码成视觉特征的模块。 负责“看图”，输出 visual tokens，例如 [B, N, Dv]。
ViT 一种视觉 Transformer 架构：把图片切成 patch，再像处理 token 一样处理 patch。 常被用作 vision encoder 的骨架，适合输出一串 patch-level visual tokens。
CLIP vision CLIP 里的视觉塔，可能是 ViT，也可能是其他视觉网络；重点是它经过图文对比学习训练。 给 VLM 提供已经具备图文语义对齐能力的视觉特征。
最容易混淆的一点：ViT 更像“网络结构名字”，CLIP vision 更像“训练过的视觉编码器来源”。很多 VLM 会使用 CLIP 训练过的 ViT 视觉塔，所以图里写成 ViT / CLIP vision。

用 Day8 的记忆来接上：ViT 先把图片切成 patch。比如一张 224 x 224 的图片，如果 patch size 是 14 x 14，就会得到 16 x 16 = 256 个 patch。每个 patch 会被投影成一个向量，再加上位置编码，送进 Transformer Encoder。 

image:          [B, 3, H, W]
patches:        [B, N, patch_dim]
patch embeddings:[B, N, Dv]
vision output:  [B, N, Dv]

这里的 N 是视觉 token 数量，通常接近 patch 数量；Dv 是视觉编码器自己的 hidden size。这个 Dv 通常和 LLM 的 hidden size Dl 不一样，所以后面必须接 projector。

Vision encoder 不负责什么

它不直接写答案，不负责聊天格式，也不直接输出“这是一只猫”这种自然语言。它只是把图片压成一组可计算的视觉特征。

Vision encoder 负责什么

它把颜色、边缘、局部形状、物体区域、文字区域、布局关系等信息编码进 visual tokens，供后面的 LLM 使用。

4. 图片如何进入 LLM

LLM 本来只会处理 token embedding。图片不能直接作为 JPG 或像素矩阵进入 LLM，必须先被视觉编码器转换成视觉 token，再经过 projector 对齐到 LLM 的 hidden size。 

image:        [B, C, H, W]
visual tokens: [B, N, Dv]
projected:     [B, N, Dl]
text tokens:   [B, T, Dl]
LLM input:     [B, N + T, Dl]
answer logits: [B, generated_steps, vocab_size]
关键类比：Day8 里图片先变成 patch token；Day6 里文本 token 进入 LLM。Day12 要把这两条线接起来：图片 token 和文本 token 都要变成同一种宽度的向量，才能进入同一个 LLM 上下文。

4.1 Step 02：四个部件如何接起来

进入 Step 02 后，把 VLM 看成四个部件的协作，而不是一个黑盒模型：vision encoder 负责看图，projector 负责换接口，LLM 负责生成，prompt template 负责组织输入格式。

部件 输入 输出 你要记住的作用
Vision encoder 图片张量 [B, 3, H, W] 视觉 token [B, N, Dv] 把图片变成可计算的视觉特征。
Projector 视觉 token [B, N, Dv] 对齐后的视觉 token [B, N, Dl] 把视觉编码器的宽度转换成 LLM 能接收的宽度。
Prompt template 用户问题、图片占位符、对话角色 模型需要的文本格式 告诉模型哪里是图片、哪里是用户问题、哪里开始回答。
LLM 对齐后的图片 token + 问题 token 答案 token 在视觉上下文和文字问题上逐 token 生成自然语言答案。
Projector 是 Step 02 的关键：它不是为了“理解图片”，而是为了让视觉 token 的维度和 LLM 的 token embedding 维度一致。没有这一步，LLM 无法把图片 token 当成自己的上下文来处理。 
# 只看形状，不看具体模型实现
image_features = vision_encoder(image)      # [B, N, Dv]
image_tokens = projector(image_features)    # [B, N, Dl]
question_tokens = embed_text(question)      # [B, T, Dl]
llm_input = concat(image_tokens, question_tokens)
answer = llm.generate(llm_input)

Prompt template 可以先理解成“对话格式模板”。比如有的模型需要把输入组织成：<image> User: 这张图里有什么？ Assistant:。这个模板不会替代模型能力，但会影响模型是否知道当前图片和问题应该如何对应。

4.2 Step 03：image tokens 如何进入 LLM 上下文

你刚才的理解很关键：VLM 最终仍然是语言模型在做下一个 token 预测。区别在于，预测下一个 token 时，LLM 看到的上下文不再只有文字 token，还包含已经投影到 Dl 宽度的 image tokens。

对象 它在 prompt 里看起来像什么 模型内部真正使用什么
图片占位符 <image> 或类似特殊 token 告诉 processor / model：这里要关联一组 projected image tokens。
用户问题 User: 这张图里有什么？ 普通文本 token embeddings，形状可以记作 [B, T, Dl]。
视觉上下文 通常不会以普通文字显示出来 projector 输出的 image tokens，形状是 [B, N, Dl]。
回答开头 Assistant: 提示 LLM 从这里开始预测答案 token。 
# 概念化的 embedding 序列，不是直接拼字符串
text_prefix = embed("User: ")
image_tokens = projector(vision_encoder(image))
question = embed("这张图里有什么？ Assistant:")

llm_context = concat(text_prefix, image_tokens, question)
next_token = LLM.predict_next_token(llm_context)
不要误解：<image> 不是图片内容本身，也不是自动生成的图片描述。它更像一个插槽，真正进入 LLM 计算的是 projector 输出的 image token embeddings。

所以你说“提示词模板是预制前置 token 信息，让大模型顺着预测下一个 token 回答问题”这个理解是对的。更精确地补一句：模板提供的是文字结构和图片插槽；图片内容本身来自 vision encoder + projector 产生的 embedding 级上下文。

4.3 Step 04：image tokens 和 text tokens 如何共同参与 attention

进入 LLM 以后，image_tokens 和 question_tokens 都已经是同一个宽度 Dl 的向量。此时它们不再是两个完全分开的系统，而是同一段上下文里的 token。LLM 的 self-attention 会在这些 token 之间计算关系。 

context = [image_1, image_2, ..., image_N, question_1, ..., question_T]

# 在 Transformer block 里，每个 token 都会生成 Q/K/V
Q = context @ Wq
K = context @ Wk
V = context @ Wv

attention_scores = Q @ K.T
attention_output = softmax(attention_scores) @ V

4.4 Q/K/V 是如何计算的

不要把 Q/K/V 理解成“先算图片 token，再算文本 token”。在一次 Transformer layer 的 forward 里，当前所有可见 token 会先堆成一个矩阵 H，然后用三套线性投影矩阵并行算出 Q、K、V。 

H = [image_1, image_2, ..., image_N, question_1, ..., question_T]
# H 的形状可以理解为 [seq_len, Dl]

Q = H @ Wq  # [seq_len, d_head * num_heads]
K = H @ Wk  # [seq_len, d_head * num_heads]
V = H @ Wv  # [seq_len, d_head * num_heads]

# 对第 i 个 token 来说
q_i = H[i] @ Wq
k_i = H[i] @ Wk
v_i = H[i] @ Wv
对象 怎么来 直观含义
H 图片 token、问题 token、prompt token 拼成的 hidden states。 当前层看到的全部上下文。
Q = H @ Wq 每个 token 的 hidden state 乘查询矩阵。 这个 token 想从上下文里找什么信息。
K = H @ Wk 每个 token 的 hidden state 乘键矩阵。 这个 token 对外声明自己能被什么查询匹配。
V = H @ Wv 每个 token 的 hidden state 乘值矩阵。 这个 token 真正提供给别人的内容。

接下来，对某个 token i，模型会用它的 q_i 去和所有可见 token 的 k_j 做相似度，然后用 softmax 得到权重，再对所有 v_j 加权求和。 

score(i, j) = q_i dot k_j / sqrt(d_head)
weight(i, j) = softmax(score(i, j))
output_i = sum_j weight(i, j) * v_j
放到 VLM 里看：回答 token 的 Q 可以去匹配图片 token 的 K，也可以匹配问题 token 的 K。匹配上以后，真正被汇入当前 hidden state 的是对应 token 的 V。

4.5 计算顺序和生成顺序

这里要分清两个层面的“顺序”：一次 forward 内部的矩阵计算，和答案 token 的自回归生成。Q/K/V 的计算在已有上下文内是并行矩阵运算；真正逐步发生的是答案生成。

一次 forward 内部

  1. 已有上下文形成 H。
  2. 所有可见 token 并行计算 Q/K/V。
  3. 每个 token 用自己的 Q 匹配可见 token 的 K。
  4. 用 attention 权重汇总对应的 V。
  5. 经过多层 Transformer，得到下一个 token 概率。

答案生成过程

  1. 输入 image tokens + question tokens。
  2. 预测第一个 answer token。
  3. 把新 token 接到上下文后面。
  4. 再次 forward，预测下一个 token。
  5. 重复直到生成结束符或达到长度限制。
关于 causal mask：如果是 LLaVA 这类 decoder-only VLM，回答 token 不能看未来 token，但可以看前面的 image tokens、prompt tokens 和 question tokens。所以图片通常作为前置上下文被答案 token 使用。

因此，image tokens 和 text tokens 共同参与计算的细节是：它们先共同形成 H，共同产生 K/V；当回答位置生成新 token 时，用当前回答位置的 Q 去检索这些 K/V，再完成下一 token 预测。

当模型回答时 attention 可以做什么 直观理解
问题 token 关注图片 token 把“图里有什么”这个问题和相关视觉区域联系起来。 问题在向图片要证据。
回答 token 关注问题 token 保持回答围绕用户问的内容，而不是随便描述图片。 回答知道自己要回答哪个问题。
回答 token 关注图片 token 生成答案时引用视觉上下文里的主体、文字、布局或关系。 答案不是凭空生成，而是读图后生成。
关键结论：VLM 不是先把图片完整翻译成一句文字再交给 LLM。更常见的理解是：图片被转换成一串 embedding 级 image tokens，它们和文本 token 一起进入 Transformer，上下文内部通过 attention 发生信息交互。

所以“预测下一个 token”仍然成立，只是预测时的上下文变丰富了：除了 prompt 和问题文字，还有一串携带视觉信息的 image tokens。

5. 图像问答流程

图像问答不是只做一次分类。模型需要读取图片特征，理解用户问题，再像 Day6 的生成式语言模型一样逐 token 生成答案。

  1. 用户提供图片和问题，例如“这张图里有什么异常？”
  2. processor 把图片整理成模型需要的视觉输入，把问题整理成文本 token。
  3. vision encoder 得到视觉 token。
  4. projector 把视觉 token 映射到 LLM 的 hidden size。
  5. LLM 在视觉 token 和问题 token 的上下文上生成回答。
  6. tokenizer decode，把输出 token 还原成自然语言。
先不要跳过第 2-4 步：很多 VLM API 会把 processor 和 projector 封装起来，但学习时必须知道它们存在，否则看起来就像“模型直接看懂了图片”。

6. Step 05：三类测试任务

现在先不急着跑模型，而是先学会设计问题。一个 VLM 如果只回答“图里有什么”，我们很难判断它到底强在哪里、弱在哪里。Day12 至少准备三类输入：场景描述、OCR / 截图、图表理解。它们分别考察不同能力。

场景描述

问模型图里有什么、主体是谁、关系是什么。用于检查基本视觉语义理解。

OCR / 截图

问图片里的文字、表单、界面元素。用于检查视觉文字识别和布局理解。

图表理解

问趋势、最大值、对比关系。用于检查模型是否能结合视觉结构和语言推理。

6.1 怎样把测试任务设计清楚

每一类测试都要同时写清楚三件事：图片应该长什么样、问题怎么问、答案应该检查什么。这样后面模型回答以后，我们不是凭感觉判断“还行”，而是能明确知道它是否读到了关键视觉证据。

任务类型 建议图片 建议问题 主要检查点
场景描述 一张有主体、背景、动作关系的普通照片，例如桌面、街景、室内工作区。 “这张图的主要内容是什么？请指出主体和它们之间的关系。” 是否能识别主体、属性、空间关系；是否会编造图中不存在的物体。
OCR / 截图 含有清晰文字的截图、海报、表单或 UI 页面。 “图中标题是什么？按钮文字是什么？页面提示用户做什么？” 是否读对文字；是否理解文字所在位置和界面功能；是否把相似字符读错。
图表理解 柱状图、折线图、饼图或简单表格，最好带标题、坐标轴和图例。 “哪个类别最高？整体趋势是什么？A 和 B 相比有什么变化？” 是否能看懂坐标轴、图例、数值大小和趋势；是否能做简单比较推理。
Step 05 的核心：测试任务不是随便找图聊天，而是用图片和问题去拆分能力。场景描述测“看懂物体和关系”，OCR / 截图测“读文字和布局”，图表理解测“视觉结构 + 语言推理”。

6.2 今天先写一个最小测试集

  1. 准备 1 张场景图，问题聚焦主体、动作、空间关系。
  2. 准备 1 张截图或文字图，问题聚焦可见文字和界面元素。
  3. 准备 1 张简单图表，问题聚焦最大值、趋势或对比关系。
  4. 每个问题旁边先写一条“人工期望答案”，后面模型输出时再对比。
不要只问开放问题：“请描述这张图”太宽泛，模型很容易给出看似流畅但不可验证的回答。学习阶段要多问可检查的问题，例如“标题是什么”“哪个柱子最高”“左侧人物在做什么”。

7. Step 06：最小 image QA 实验计划

现在进入下一阶段：从“理解架构”过渡到“准备最小脚本”。这一步的目标不是评测模型强弱，也不是马上下载大模型，而是把单图单问答的推理链路拆清楚：图片和问题如何进入 processor，模型如何生成答案，输出时要记录哪些边界信息。

Step 06 的目标：先准备一个最小 image_qa.py 脚本设计。它只处理一张图片、一个问题、一次回答，并打印模型、设备、耗时、答案和失败原因。

7.1 最小脚本应该长什么样

VLM 推理脚本不要一开始就写成完整评测框架。先保持最小闭环：参数进入、模型加载、图片读取、prompt 组装、生成答案、输出记录。不同 VLM 的具体类名和 chat template 可能不同，但主线结构基本一致。

脚本部分 负责什么 先观察什么
命令行参数 接收 --image、--question、--model、--device。 输入是否清楚，图片路径是否存在。
processor 把图片和文本整理成模型需要的张量、token ids、attention mask。 它是连接“原始输入”和“模型输入”的入口。
model 加载 vision encoder、projector、LLM 等参数，执行 generate。 是否能放到目标设备，是否需要半精度或量化。
decode 把生成的 token ids 还原成自然语言答案。 输出是否只包含新答案，是否混入 prompt。
记录信息 打印耗时、设备、显存、模型名、问题、答案。 以后比较不同图片和模型时有依据。 
# 伪代码：不绑定某一个具体 VLM 类名
args = parse_args()
image = load_image(args.image)
question = args.question

processor = load_processor(args.model)
model = load_vlm_model(args.model, device=args.device)

inputs = processor(image=image, text=question)
inputs = move_to_device(inputs, args.device)

with inference_mode():
    output_ids = model.generate(**inputs, max_new_tokens=128)

answer = decode_new_tokens(output_ids)
print(answer)
print(runtime, device, model_name, failure_boundary)

7.2 先把模型边界说清楚

真实 VLM 比 CLIP 更重，因为它通常同时包含视觉塔、projector 和语言模型。Day12 的脚本默认应该是本地优先、离线优先；只有明确允许下载时，才去拉远程权重。

先选轻量模型

目标是跑通链路，不是追求最好效果。轻量模型更容易暴露输入格式、设备、显存和 decode 细节。

默认不下载

如果本地没有权重，脚本应该清楚提示缺少模型，而不是静默联网下载。这样实验可控，也方便复现。

不要跳过边界记录：如果模型跑不起来，也要记录失败原因：缺依赖、缺权重、显存不够、processor 不匹配、chat template 不匹配，还是 decode 出错。

7.3 第一次运行要记录什么

最小实验不是只看答案好不好，而是确认整个 VLM 推理链路是否真实跑通。第一次记录越具体，后面排错越轻松。

记录项 为什么要记录
模型名称和加载方式 确认用的是本地缓存、指定路径，还是远程模型名。
设备和精度 确认是 CPU、CUDA，还是其他设备；后续解释速度和显存。
图片路径和问题 确保答案可以回溯到具体输入，不混淆测试样例。
生成参数 例如 max_new_tokens、是否采样；这些会影响答案长度和稳定性。
耗时和失败信息 记录模型能不能实际运行，以及瓶颈在哪里。
下一步真正写脚本时的判断标准：能用一条命令完成“输入图片 + 输入问题 + 输出答案 + 打印运行信息”，就算 Day12 的最小 image QA 闭环跑通。
