2. 从 Day9 到 Day10

Day9 你已经掌握了这条链路： 

images -> image_encoder -> image_embeddings
texts  -> text_encoder  -> text_embeddings

similarity = image_embeddings @ text_embeddings.T

Day10 不改变这条链路。Day10 只是多做一步：把 similarity 里的分数排序。 

similarity matrix
-> sort / topk
-> ranked results
-> return top 1 / top 5 / top k

关键变化：Day9 关心“这对图文是不是匹配”；Day10 关心“在一堆候选里，谁最匹配”。这就是从 alignment 到 retrieval 的跨越。

3. 检索任务是什么

检索任务里有两个常用词：query 和 gallery。

概念 直观含义 CLIP 图文检索里的例子
query 你拿来发起搜索的东西。 一张图片，或者一句文本。
gallery 被搜索的候选库。 一批候选文本，或者一批候选图片。
top-k 按相似度从高到低取前 K 个结果。 返回最像 query 的前 3 条文本，或前 5 张图片。

3.1 图搜文：image-to-text retrieval

给一张图片，从一批候选文本里找最匹配的描述。 

query image:
  一张红色方块图片

text gallery:
  0. "a red square on a white background"
  1. "a blue circle on a white background"
  2. "a dog running on grass"
  3. "a bowl of noodles"

CLIP 会给这张图片和每条文本打分，然后按分数排序。最高分文本就是 top-1，前 K 个文本就是 top-k。

3.2 文搜图：text-to-image retrieval

给一句文本，从一批候选图片里找最匹配的图片。 

query text:
  "a red square on a white background"

image gallery:
  image 0: red square
  image 1: blue circle
  image 2: dog
  image 3: noodles

这和图搜文是同一张相似度矩阵的另一个方向。图搜文通常按行排序，文搜图通常按列排序或使用转置后的行排序。

4. 相似度矩阵如何变成检索

假设我们有 3 张图片和 4 条文本： 

image_embeddings.shape = [3, D]
text_embeddings.shape  = [4, D]

scores = image_embeddings @ text_embeddings.T
scores.shape = [3, 4]

这张 [3, 4] 表里的每一行都可以做一次“图搜文”： 

scores[0] = image 0 对所有 texts 的分数
scores[1] = image 1 对所有 texts 的分数
scores[2] = image 2 对所有 texts 的分数

每一列也可以做一次“文搜图”： 

scores[:, 0] = text 0 对所有 images 的分数
scores[:, 1] = text 1 对所有 images 的分数
scores[:, 2] = text 2 对所有 images 的分数
scores[:, 3] = text 3 对所有 images 的分数

4.1 top-k 是什么

如果某一行分数是： 

image 0 scores over texts = [0.82, 0.13, 0.05, 0.41]

从高到低排序： 

rank 1: text 0, score 0.82
rank 2: text 3, score 0.41
rank 3: text 1, score 0.13
rank 4: text 2, score 0.05

如果 k = 2，那么 top-2 结果就是 text 0 和 text 3。

不要把 top-k 想复杂：它不是新模型，也不是新 loss。它只是对相似度分数排序，然后取前 K 个。

5. 最小 toy retrieval demo：把排名跑出来

现在进入 Day10 的代码阶段。这个 demo 仍然不加载真实 CLIP，不下载模型，不训练参数。它只用手写向量模拟 image_embeddings 和 text_embeddings，把检索最核心的工程动作跑清楚。

脚本位置：experiments/day-10-clip-retrieval/clip_retrieval_toy_demo.py。运行命令如下： 

.venv/bin/python experiments/day-10-clip-retrieval/clip_retrieval_toy_demo.py

5.1 这个脚本在模拟什么

真实 CLIP 里，图片向量和文本向量来自 image encoder、text encoder 和 projection head。toy demo 里我们暂时手写这些向量，目的是把 retrieval 的骨架看清楚。 

image_embeddings [num_images, D]
text_embeddings  [num_texts, D]

scores = image_embeddings @ text_embeddings.T
scores.shape = [num_images, num_texts]

这次脚本设置了 4 张图片、6 条文本，所以： 

image_embeddings.shape = [4, 5]
text_embeddings.shape  = [6, 5]
scores.shape           = [4, 6]

这里的 D = 5 是人为设计的小语义空间，用来表示几个粗略特征：red、blue、dog、food、roundness。真实 CLIP 的 D 通常是 512 或其他配置维度，而且不是我们手写，而是模型算出来。

5.2 检索库：query 和 gallery 如何对应

脚本里有 4 个 image items： 

0: image 0: red square
1: image 1: blue circle
2: image 2: dog on grass
3: image 3: bowl of noodles

还有 6 个 text items： 

0: "a red square on a white background"
1: "a blue circle on a white background"
2: "a dog standing on grass"
3: "a bowl of noodles on a table"
4: "a red circle on a poster"
5: "a dog near a blue ball"

对图搜文来说，4 张图片逐个作为 query，6 条文本是 gallery。对文搜图来说，6 条文本逐个作为 query，4 张图片是 gallery。

5.3 相似度矩阵输出怎么读

运行脚本后，核心矩阵是： 

scores.shape = (4, 6)
scores =
tensor([[0.9999, 0.1423, 0.0104, 0.0797, 0.7360, 0.0673],
        [0.1317, 1.0000, 0.1117, 0.2088, 0.5681, 0.6619],
        [0.0160, 0.1747, 0.9980, 0.0296, 0.0796, 0.8530],
        [0.0746, 0.2286, 0.0172, 0.9995, 0.2777, 0.1388]])

第 0 行表示 image 0: red square 对所有文本的分数。你会看到 text 0 分数最高，text 4 也不低，因为它也包含 red 和 circle 这类相近因素。

5.4 torch.topk(scores, k, dim=1) 到底做什么

图搜文时，我们对 scores 的每一行做 top-k： 

values, indices = torch.topk(scores, k=3, dim=1)
  • dim=1：沿着列方向排序，也就是每张图片在所有文本里找 top-k。
  • values：top-k 的相似度分数。
  • indices：top-k 对应的 gallery 下标，也就是文本编号。

对 image 0，输出是： 

Query 0: image 0: red square
  rank 1: column 0 | score = 0.9999 | text 0: "a red square on a white background"
  rank 2: column 4 | score = 0.7360 | text 4: "a red circle on a poster"
  rank 3: column 1 | score = 0.1423 | text 1: "a blue circle on a white background"

这就是一个最小检索结果。不是概率解释，也不是生成答案，而是“按相似度排队”。

5.5 文搜图为什么用 scores.T

文搜图时，query 变成文本，gallery 变成图片。为了继续使用“每一行是一个 query”的读法，脚本直接对 scores.T 做 top-k： 

values, indices = torch.topk(scores.T, k=3, dim=1)

例如： 

Query 0: text 0: "a red square on a white background"
  rank 1: column 0 | score = 0.9999 | image 0: red square
  rank 2: column 1 | score = 0.1317 | image 1: blue circle
  rank 3: column 3 | score = 0.0746 | image 3: bowl of noodles

5.6 Recall@K 先有一个直觉

脚本最后还打印了一个非常小的检索评估： 

image-to-text Recall@1 = 1.000
image-to-text Recall@3 = 1.000
text-to-image Recall@1 = 1.000
text-to-image Recall@3 = 1.000

Recall@K 问的是：正确答案有没有出现在前 K 个结果里。这个 toy demo 是我们手写出来的干净例子，所以结果是满分。真实检索里，Recall@1 和 Recall@5 经常会不同，因为正确项可能不是第一名，但可能在前 5 名里。

本阶段最重要的一句话：检索不是新模型，它是对 CLIP 相似度矩阵做排序。图搜文排 scores 的行，文搜图排 scores.T 的行，topk_indices 给出最终命中的 gallery 下标。

6. 真实 CLIP retrieval demo：多图片、多文本双向检索

Toy demo 让我们看懂了排序机制。现在换成真实 CLIP：图片和文本向量不再手写，而是由 CLIPModel 真实算出来。

脚本位置：experiments/day-10-clip-retrieval/clip_real_retrieval_demo.py。默认离线加载本地缓存；如果没有缓存，才需要你显式加 --allow-download。 

.venv/bin/python experiments/day-10-clip-retrieval/clip_real_retrieval_demo.py

6.1 真实 demo 和 toy demo 的区别

部分 Toy retrieval demo 真实 CLIP retrieval demo
图片向量 手写小向量，例如 [red, blue, dog, food, roundness]。 真实 CLIPModel 从图片像素算出 outputs.image_embeds。
文本向量 手写小向量。 真实 CLIPModel 从 token ids 算出 outputs.text_embeds。
分数矩阵 image_embeddings @ text_embeddings.T outputs.logits_per_image
检索动作 torch.topk 仍然是 torch.topk

为了让脚本不依赖外部图片文件，默认会生成 4 张简单图片： 

Image gallery:
  0: image 0: generated red square
  1: image 1: generated blue circle
  2: image 2: generated green triangle
  3: image 3: generated noodle bowl drawing

候选文本是 7 条，其中前 4 条有对应图片，后 3 条是干扰项： 

Text gallery:
  0: "a red square on a white background"
  1: "a blue circle on a white background"
  2: "a green triangle on a white background"
  3: "a bowl of noodles on a table"
  4: "a photo of a dog on grass"
  5: "a city street at night"
  6: "a person riding a horse"

6.3 真实模型输出 shape

本机已经有 openai/clip-vit-base-patch32 缓存，所以默认离线模式直接跑通。关键 shape 是： 

pixel_values.shape = (4, 3, 224, 224)
		input_ids.shape = (7, 9)
		attention_mask.shape = (7, 9)

		outputs.image_embeds.shape = (4, 512)
	outputs.text_embeds.shape = (7, 512)
	outputs.logits_per_image.shape = (4, 7)
	outputs.logits_per_text.shape = (7, 4)

这正好对应 Day10 的检索结构：4 张图片对 7 条文本得到 [4, 7] 分数表，7 条文本对 4 张图片得到 [7, 4] 分数表。

6.4 图搜文结果怎么读

对每张图片，脚本从 7 条文本里取 top-3。几个关键结果如下： 

Query 0: image 0: generated red square
  rank 1: text 0 | score = 32.4416 | "a red square on a white background"
  rank 2: text 2 | score = 26.0646 | "a green triangle on a white background"
  rank 3: text 1 | score = 25.6983 | "a blue circle on a white background"

Query 1: image 1: generated blue circle
  rank 1: text 1 | score = 35.1748 | "a blue circle on a white background"

Query 2: image 2: generated green triangle
  rank 1: text 2 | score = 36.4383 | "a green triangle on a white background"

Query 3: image 3: generated noodle bowl drawing
  rank 1: text 3 | score = 30.7429 | "a bowl of noodles on a table"

前 4 个有明确对应关系的样例都排到了 top-1。这说明真实 CLIP 已经能把这些简单图形和英文描述放到接近的位置。

6.5 文搜图结果里的边界

文搜图时，前 4 条文本也能找回对应图片： 

text 0: red square    -> rank 1 image 0: red square
text 1: blue circle   -> rank 1 image 1: blue circle
text 2: green triangle -> rank 1 image 2: green triangle
text 3: noodles       -> rank 1 image 3: noodle bowl drawing

但注意后 3 条文本没有对应图片： 

Query 4: "a photo of a dog on grass"
  rank 1: image 2: generated green triangle

Query 5: "a city street at night"
  rank 1: image 3: generated noodle bowl drawing

Query 6: "a person riding a horse"
  rank 1: image 2: generated green triangle

这不是模型“真的认为三角形是狗”。检索系统必须在给定 gallery 里返回最相似的候选，即使候选库里根本没有正确答案。真实业务里通常要配合阈值、重排、人工审核或更大的候选库，避免把“候选库里最像的错误答案”当成可靠答案。

重要边界：top-k 检索只保证“从候选库里排出最像的 K 个”，不保证候选库里一定存在正确答案。没有正确答案时，它也会返回一个 rank 1。

本阶段最重要的一句话：真实 CLIP retrieval 和 toy retrieval 的工程动作完全一致，区别只在于 embedding 的来源：toy demo 手写向量，真实 demo 用 CLIPModel 计算向量。

7. 检索评估与无答案判断

只会返回 top-k 还不够。一个检索系统还要回答两个更工程化的问题：正确答案有没有被找回来？如果候选库里根本没有正确答案，系统要不要拒绝返回？

7.1 Recall@K 到底在评估什么

Recall@K 的问题很具体：对有标准答案的 query，正确候选是否出现在前 K 个结果里。 

Recall@1 = 正确答案在 rank 1 的 query 数 / 有标准答案的 query 总数
Recall@3 = 正确答案在 rank 1 到 rank 3 的 query 数 / 有标准答案的 query 总数

注意这里的分母不是所有 query。默认 demo 里只有前 4 条文本有对应图片，后 3 条文本在图片库里没有答案，所以 Recall@K 只统计前 4 条有标准答案的 query。无答案 query 要用另一套逻辑评估。 

image-to-text Recall@1 = 1.000
text-to-image Recall@1 = 1.000
image-to-text Recall@3 = 1.000
text-to-image Recall@3 = 1.000

7.2 为什么需要阈值

top-k 的职责是排序，不是判断“有没有答案”。如果 gallery 里没有狗、没有城市街道、没有骑马的人，CLIP 仍然会从现有 4 张图里选出分数最高的一张。这个最高分只是“候选库里相对最高”，不等价于“真的匹配”。 

top1_score >= accept_threshold -> 接受这个检索结果
top1_score <  accept_threshold -> 拒绝返回，认为候选库里没有足够可信的答案

阈值不是通用常数：这里的 accept_threshold = 28.0 只是为了教学，在当前模型、当前 prompts、当前合成图片上刚好能区分有答案和无答案。真实系统必须用验证集重新校准阈值，不能直接照搬。

8. 最小图片搜索 Demo：从脚本到可用工具

前面的脚本已经证明 CLIP 可以做文搜图。最后一步是把它封装成一个真正能点开的本地小工具：输入文本 query，后端跑 CLIP，前端展示 top-3 和阈值判断。

Demo 位置：demos/clip-image-search/。运行命令如下： 

.venv/bin/python demos/clip-image-search/app.py

启动后访问： 

http://127.0.0.1:8010

8.1 这个 demo 的真实调用链

browser input query
-> GET /api/search?q=...
-> processor(text=[query], images=gallery)
-> CLIPModel.forward()
-> outputs.logits_per_text.shape = [1, 4]
-> torch.topk(scores, k=3)
-> threshold accept/reject
-> JSON response
-> browser renders ranked images

这里的 [1, 4] 很重要：当前只有 1 条文本 query，gallery 里有 4 张图片，所以输出是一行 4 列。每一列就是这条文本对某张图片的 CLIP 分数。

8.2 文件结构

文件 职责
demos/clip-image-search/app.py 启动本地 HTTP 服务，加载 CLIP，生成默认图片库，提供 /api/gallery 和 /api/search。
demos/clip-image-search/index.html 搜索输入、阈值输入、preset query、top-3 展示和 accept/reject 状态。
demos/clip-image-search/README.md 记录运行方式和核心数据流。

8.3 两个 API 验证结果

有答案 query：红色方块。

decision = accept

rank 1 = generated red square
logits_per_text.shape = [1, 4]

无答案 query：狗在草地上。gallery 里没有狗，所以 top-1 虽然会返回三角形，但阈值判断会拒绝它。

8.4 这还不是工业级检索系统

当前 demo 每次 query 都直接对 4 张图片做一次 CLIP forward。真实系统不会这么做：图片库通常会提前离线编码成 image embeddings，再放进向量数据库或 ANN 索引；线上 query 只需要编码文本，再用向量检索找最近图片。

工程边界：这个 demo 是教学用最小闭环，不是高性能检索服务。它保留了最关键的真实结构：query、gallery、CLIP score、top-k、threshold。

8.5 工业界如何处理“候选库没有正确答案”

生产环境里，系统通常并不知道“正确答案是否存在”。训练和离线评估时有标签，所以我们知道某个 query 的正确图片或文字是谁；线上真实用户发起 query 时，没有一个 oracle 直接告诉系统“库里有没有答案”。系统只能根据检索分数、业务规则和历史反馈，判断“当前 top-k 是否足够可信”。

处理策略 解决的问题 例子
分数阈值 top-1 分数太低时拒绝返回。 top1_score < threshold 时显示“没有找到足够相关的结果”。
margin 阈值 top-1 和 top-2 太接近时说明模型不确定。 top1_score - top2_score 太小，则返回多个候选或要求用户补充 query。
重排器 reranker 第一阶段召回粗糙，第二阶段用更强模型重新判断。 先用向量库召回 top-50，再用 cross-encoder 或更强 VLM 检查 top-10。
元数据和过滤 减少明显错误候选。 按时间、地点、类目、权限、商品状态过滤后再检索。
人工或用户反馈 线上没有标签，需要逐步收集监督信号。 点击、停留、收藏、举报、人工标注、A/B 实验。

所以更准确的表述是：生产系统不是“知道没有正确答案”，而是“判断当前结果不够可信，于是选择拒答、降级、让用户改写 query，或返回多个候选并标注不确定”。 

线上 query 没有标准答案
-> 模型只给 score 和 ranking
-> 系统用 threshold / margin / reranker / metadata 判断可信度
-> 可信：返回结果
-> 不可信：拒答、降级、请求澄清或进入人工流程

本阶段最重要的一句话：Day10 的最终 demo 已经从“矩阵排序”变成了“可交互检索工具”。它仍然没有训练模型，只是把 CLIP 推理结果组织成一个完整的 retrieval workflow。

9. Day10 收口

Day10 已经从“相似度矩阵”推进到“本地图片搜索 demo”，本日学习任务可以收口。

  1. Day10 的任务是把 Day9 的相似度矩阵变成可用的检索排名。
  2. query 是发起搜索的东西，gallery 是被搜索的候选库。
  3. 图搜文是给图片找文本，文搜图是给文本找图片。
  4. scores = image_embeddings @ text_embeddings.T 仍然是核心。
  5. 按行排序可以做 image-to-text retrieval。
  6. 按列排序，或对 scores.T 按行排序，可以做 text-to-image retrieval。
  7. top-k 就是按相似度从高到低取前 K 个结果。
  8. torch.topk(scores, k, dim=1) 会对每一行单独取前 K 个分数和下标。
  9. topk_values 是分数，topk_indices 是 gallery 里的候选编号。
  10. Recall@K 检查正确答案是否出现在前 K 个结果里。
  11. 真实 CLIP retrieval 仍然是对 outputs.logits_per_image 和 outputs.logits_per_text 做 top-k。
  12. 如果 gallery 里没有正确答案，top-k 仍然会返回“相对最像”的候选，因此检索结果需要边界判断。
  13. Recall@K 只适合评估有标准答案的 query；无答案 query 要用阈值、拒答或人工审核等逻辑处理。
  14. 默认真实 demo 记录了 4 个成功案例和 3 个无答案失败边界；阈值 28.0 在这组教学样例上能把它们分开。
  15. demos/clip-image-search/ 把检索脚本封装成了本地 Web 工具。
  16. 这个 Web demo 的核心输出是 logits_per_text.shape = [1, 4]：1 条文本 query 对 4 张候选图片打分。
  17. 工业级检索通常会提前离线编码图片库，而不是每次 query 都重新编码所有图片。
  18. 生产环境没有 oracle 直接告诉系统“正确答案是否存在”；系统只能根据阈值、margin、重排器、元数据和反馈闭环判断结果是否可信。
