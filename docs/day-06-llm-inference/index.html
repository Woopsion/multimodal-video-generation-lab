0. 当前学习目标

Day6 的第一阶段只解决一个问题：当你输入一段文字时，LLM 到底如何一步步生成下一个 token。

先建立主线：prompt 文本不是直接喂给神经网络。神经网络只处理数字，所以必须先经过 tokenizer，把文字变成一串整数 id，也就是 input_ids。

1. LLM 推理总流程

LLM 生成文本的核心循环可以先记成一句话：已有 token 进去，模型预测下一个 token，把新 token 拼回去，再继续预测。 

prompt text
-> tokenizer.encode
-> input_ids
-> token embedding + position embedding
-> causal transformer blocks
-> logits
-> choose next_token_id
-> append next_token_id to input_ids
-> repeat
-> tokenizer.decode

和 Day3 的类比：MNIST 最后输出 10 个 logits，分别对应 10 个数字类别。LLM 最后输出的是对整个词表的 logits，如果词表有 50000 个 token，就会有 50000 个分数。

2. prompt 如何变成 input_ids

prompt 是你输入给模型的原始文本。比如 "我喜欢"。但是神经网络不能直接处理“我”这个字，也不能直接处理“喜欢”这个词。它只能处理数字张量。

所以中间需要一个 tokenizer。它通常做两件事：先把文本切成 token，再根据词表把每个 token 映射成一个整数 id。

token 是什么

token 是 tokenizer 切出来的最小处理单位。它可能是一个字、一个词、一个词的一部分，也可能包含空格或符号。

对中文来说，tokenizer 可能把 "我喜欢深度学习" 切成 ["我", "喜欢", "深度", "学习"]，也可能切成别的形式。具体怎么切由 tokenizer 的词表和规则决定。

token id 是什么

token id 是 token 在词表里的编号。它不是向量，也不是“语义详情”，只是一个整数索引。

类比 Day5 的 embedding 表：如果 token id 是 205，就表示去 token embedding 表的第 205 行取出这个 token 的向量。

一个只用于理解的例子

下面的 id 是为了帮助理解而编的示意数字，不代表真实 tokenizer 的输出。真实模型的 id 要由它自己的 tokenizer 决定。

我id 101
喜欢id 205
深度学习id 309
。id 17
prompt = "我喜欢"
tokens = ["我", "喜欢"]
input_ids = [101, 205]

关键点：input_ids 里存的不是 token 的完整信息，也不是 token 向量。它只是一串整数编号。真正的向量要等进入 nn.Embedding 之后才出现。

3. token id 到向量

模型内部不能直接用 [101, 205] 做复杂语义计算。这个整数序列必须先进入 token embedding 表。embedding 表可以理解成一个巨大的可学习矩阵。

token_embedding_table.shape = [V, C]
input_ids.shape = [B, T]
token_vectors = embedding(input_ids)
token_vectors.shape = [B, T, C]
符号 含义 通俗理解
V vocab size，词表大小 词表里一共有多少个 token。比如 50000，就有 50000 个可被预测的候选 token。
C embedding dimension，向量维度 每个 token 用多少个数字描述。Day5 里我们用过 embed_dim。
B batch size，批大小 一次送进模型多少条序列。学习阶段可以先假设 B = 1。
T sequence length，序列长度 当前这条输入里有多少个 token。

token embedding 和 position embedding 会相加

token embedding 表示“这个 token 大概是什么”。position embedding 表示“这个 token 在第几个位置”。LLM 和 Day5 一样，通常会把这两类向量相加，得到每个位置真正送入 Transformer Block 的输入向量。 

token_vector    = token_embedding(input_ids)
position_vector = position_embedding(position_ids)
model_input     = token_vector + position_vector

4. Causal LM：为什么只能看左边

Causal Language Model 可以翻译成“因果语言模型”或“自回归语言模型”。这里的 causal 不是哲学里的因果关系，而是一个生成约束： 模型在生成第 t + 1 个 token 时，只能使用第 0 到第 t 个 token 的信息。

换成人话：如果当前 prompt 是 "我 喜欢"，模型要预测后面接什么。它可以看见 "我" 和 "喜欢"，但不能提前看见答案 "深度学习"。因为真实生成时，"深度学习" 还没有被模型生成出来。

Day5 Encoder

Encoder 的 self-attention 通常可以让每个 token 看见整个输入序列。适合做理解、分类、提取表示。

Day6 Causal LM

Causal LM 生成时必须从左到右。第 3 个位置不能看第 4 个位置，因为第 4 个 token 当时还没生成出来。

先说清楚：attention 矩阵的一行一列是什么

假设输入被切成 4 个 token：

我位置 0
喜欢位置 1
深度学习位置 2
。位置 3

Self-Attention 会给每个 token 重新算一个新向量。算“位置 2 的 token 的新向量”时，位置 2 会拿自己的 Query 去和别的位置的 Key 打分。这个分数矩阵可以写成：

attention_scores[t, j] = 第 t 个 token 看第 j 个 token 的原始分数
矩阵方向 含义 具体例子
纵向，一行一行看 正在被更新的 token。也就是“现在轮到谁计算自己的新向量”。 第 2 行表示：现在正在给位置 2 的 深度学习 算新向量。
横向，一列一列看 候选来源 token。也就是“当前 token 可以从谁那里拿信息”。 第 0 列表示：能不能看位置 0 的 我，以及看它的分数是多少。
某一个格子 attention_scores[t, j]，表示第 t 个 token 对第 j 个 token 的注意力打分。 attention_scores[2, 0] 表示：深度学习 在更新自己时，看 我 的原始分数。

为什么右上角是禁止的

看第 2 行。第 2 行表示“正在给位置 2 的 token 算新向量”。它可以看位置 0、1、2，因为这些位置在它左边或就是它自己；但它不能看位置 3、4，因为位置 3、4 是未来 token。 

第 2 行的含义：
正在更新位置 2 的 token

允许看：位置 0、位置 1、位置 2
禁止看：位置 3、位置 4

原因：
生成到位置 2 时，位置 3 和位置 4 还不存在。
如果训练时允许偷看未来，模型就学会了作弊，推理生成时会对不上。

“attention 打分时禁止看见”具体是什么意思

不是把 token id 删除，也不是把 embedding 删除。真正发生的位置在 attention 分数矩阵里。原始分数算出来以后，未来位置对应的分数会被改成一个极小的数，常见写法是 -inf 或者一个很大的负数。

原始分数：score[t, j] = q_t 和 k_j 的匹配分数
如果 j > t：masked_score[t, j] = -inf
softmax(-inf) = 0
所以未来 token 的 attention weight = 0

这里每个符号的含义：

符号 含义
t 正在更新的 token 位置。比如 t = 2 表示正在更新第 2 个位置的 token。
j 被看的 token 位置。比如 j = 0 表示去看第 0 个位置的 token。
j > t 被看的位置在当前 token 的右边，也就是未来位置，所以必须禁止。
-inf 负无穷。实际代码里常用一个极大的负数近似。经过 softmax 后，这个位置的权重会变成 0。

一个具体数字例子

假设第 2 个 token 原本对 5 个位置的 attention score 是下面这样。注意这里还没有 softmax。 

正在更新位置 t = 2 的 token
原始分数：
[ 1.2, 0.4, 2.0, 3.7, 0.8 ]
  j0   j1   j2   j3   j4

causal mask 后：
[ 1.2, 0.4, 2.0, -inf, -inf ]
  j0   j1   j2    j3    j4

softmax 后：
[0.27, 0.12, 0.61, 0.00, 0.00]

最后算新向量时，位置 2 只会混合位置 0、1、2 的 Value。位置 3、4 的权重是 0，所以完全拿不到未来 token 的内容。

重点：Causal mask 的本质是“让未来位置在 softmax 后权重变成 0”。这样每个 token 更新自己的向量时，只能从自己和左边 token 聚合信息，不能从右边未来 token 聚合信息。

5. logits 与下一个 token

经过多层 Causal Transformer Block 之后，模型会输出 logits。你可以把 logits 先理解成“原始分数”，它还不是概率。

Day3 的 MNIST 分类输出 10 个 logits，因为类别只有 10 个数字。LLM 的输出类别是整个词表里的 token，所以如果词表大小是 V，每个位置都会输出 V 个 logits。也就是说，LLM 在每个位置都做一次“从词表所有 token 中选下一个 token”的分类判断。

logits.shape = [B, T, V]
B = batch size，表示一次有几条序列
T = 当前输入序列的 token 数量
V = vocab size，表示词表里有多少个 token

logits 是从哪里来的

Transformer Block 的输出还不是词表分数。它输出的是每个位置的隐藏向量，常见 shape 是 [B, T, C]。然后模型最后接一个线性层，常叫 lm_head，把每个位置的 C 维向量转换成 V 个词表分数。

hidden_states.shape = [B, T, C]
lm_head.weight.shape = [V, C]
logits = lm_head(hidden_states)
logits.shape = [B, T, V]

这里的 C 是模型内部每个 token 向量的维度，和 Day5 的 D 是同类概念。V 是词表大小。lm_head 的作用就是把“内部向量空间”翻译成“词表每个 token 的分数”。

一个 logit 到底怎么算出来

先只看一个 batch、最后一个位置、一个候选 token。假设候选 token 是 "深度学习"，它在词表里的 id 是 4。那么 logits[0, -1, 4] 就表示： 第 0 条输入的最后一个位置认为“下一个 token 是深度学习”的原始分数。

logits[b, t, i] = sum(hidden_states[b, t, k] * lm_head.weight[i, k], k = 0 到 C - 1)
符号 含义
b batch 中第几条输入。学习 demo 里通常是 0。
t 当前 token 位置。生成下一个 token 时一般取最后一个位置，所以代码里写 -1。
i 候选 token id。比如 i = 4 表示候选 token 是 "深度学习"。
k 隐藏向量内部第几个维度。若 C = 6，那 k 从 0 到 5。
hidden_states[b, t, k] 第 b 条输入、第 t 个位置的隐藏向量中第 k 个数。
lm_head.weight[i, k] lm_head 中候选 token i 对第 k 个隐藏维度的权重。

所以 lm_head(hidden_states) 并不神秘。它是在每个位置上，把这个位置的隐藏向量分别和词表里每个 token 的输出权重行做点积。做完以后，一个位置就得到 V 个分数。 

last_hidden.shape = [C]
weight_for_深度学习.shape = [C]

logit_for_深度学习 =
  last_hidden[0] * weight_for_深度学习[0]
+ last_hidden[1] * weight_for_深度学习[1]
+ ...
+ last_hidden[C-1] * weight_for_深度学习[C-1]

为什么只看最后一个位置的 logits

假设当前输入是 ["我", "喜欢"]，位置分别是 0 和 1。模型会输出两个位置的 logits：

位置 这个位置已经看见了什么 这个位置的 logits 负责预测什么
位置 0：我 只能看见 我 训练时负责预测下一个 token：喜欢
位置 1：喜欢 可以看见 我 和 喜欢 推理时负责预测 prompt 后面的下一个 token，比如 深度学习

所以生成下一个 token 时，通常只看最后一个位置 T - 1 的 logits。因为它是“读完整个 prompt 之后”的那个位置。 

input_ids = [101, 205]
logits.shape = [1, 2, 50000]

# 只拿最后一个位置
next_token_logits = logits[0, -1, :]
next_token_logits.shape = [50000]

-1 的意思：logits[0, -1, :] 里的 -1 表示取序列维度上的最后一个位置。这里输入有 2 个 token，最后一个位置就是位置 1，也就是 "喜欢" 对应的位置。

logits 的每一个位置为什么对应一个 token

词表会规定 token id 和 token 的对应关系。比如示意词表里，309 对应 "深度学习"。那么 next_token_logits[309] 就是模型给“下一个 token 是 深度学习”这件事打的原始分数。 

vocab[309] = "深度学习"
vocab[415] = "电影"
vocab[17]  = "。"

next_token_logits[309] = 8.2   # “下一个 token 是 深度学习”的分数
next_token_logits[415] = 4.1   # “下一个 token 是 电影”的分数
next_token_logits[17]  = 1.3   # “下一个 token 是 。”的分数

这里的顺序不是模型临时发明的，而是 tokenizer 的词表提前规定好的。第 309 个位置就永远对应 token id 309。模型训练的过程，就是让这些位置上的分数逐渐变得合理。

从 logits 到概率

后续学习 sampling 时会展开。现在先只看最基本的 softmax：它会把每个 token 的原始分数转换成概率，并且所有概率加起来等于 1。

p_i = exp(z_i) / sum(exp(z_j), j = 0 到 V - 1)
符号 含义
z_i 第 i 个 token 的 logit，也就是模型给这个候选 token 的原始分数。
exp(z_i) 以自然常数 e 为底的指数函数，也就是 e 的 z_i 次方，作用是把分数变成正数。
sum(exp(z_j), j = 0 到 V - 1) 把词表里所有候选 token 的 exp(logit) 加起来，作为归一化分母。
p_i 第 i 个 token 被选为下一个 token 的概率。

具体例子

还是用示意词表。模型读完 "我喜欢" 后，只取最后一个位置的 next_token_logits。如果 "深度学习" 的分数最高，那么最简单的 greedy decoding 会选择它。

候选 token token id logit 原始分数 可能的结果
深度学习 309 8.2 最高，可能被选中
电影 415 4.1 也可能，但分数低很多
。 17 1.3 概率较低 
next_token_id = 309
new_input_ids = [101, 205, 309]
decoded_text = "我喜欢深度学习"

一句话收口：logits 不是最终文字，而是“词表每个 token 的候选分数表”。生成时先从最后一个位置的 logits 里选出一个 token id，再把这个 id append 回 input_ids，然后继续下一轮。

6. shape 总表

这部分先建立 Day6 最重要的 shape 直觉。后面写代码时，我们会像 Day5 一样逐行打印这些 shape。

prompt
普通字符串，例如 "我喜欢"。
tokens
tokenizer 切出来的 token 列表，例如 ["我", "喜欢"]。
input_ids
整数 id 张量，常见 shape 是 [B, T]。
embedding output
每个 token id 查表后得到的向量，shape 是 [B, T, C]。
logits
每个位置对词表所有 token 的分数，shape 是 [B, T, V]。
next_token_logits
最后一个位置的词表分数，shape 是 [V] 或 [B, V]。

8. Part 3：Sampling 采样策略

模型算出 next_token_logits 之后，还没有真正生成文字。Sampling 解决的是最后一步：从词表候选 token 里选出一个 next_token_id。

先抓主线：模型负责给每个候选 token 打分；sampling 策略负责根据这些分数选择一个 token。模型能力和 sampling 策略是两件事，sampling 不能让模型知道它本来不知道的知识。

运行入口

.venv/bin/python experiments/day-06-llm-inference/sampling_strategy_demo.py

从 logits 到选择 token 的四步

步骤 对象 含义
1 next_token_logits 最后一个位置对词表所有 token 的原始分数，shape 是 [V]。
2 temperature 可选。先调整 logits 的尖锐程度，影响高分 token 和低分 token 的差距。
3 softmax 把 logits 转成概率分布，所有候选 token 的概率加起来等于 1。
4 greedy / sampling / top_p 根据策略从概率分布里选出一个 token id。

Greedy Decoding：永远选最高分

Greedy decoding 可以翻译成“贪心解码”。它不随机，不抽样，只做一件事：找到 logit 最大的 token id。

next_token_id = argmax(next_token_logits)

argmax 的意思是“返回最大值所在的位置”。如果 "深度学习" 的 logit 最大，那么 greedy 就一定选择 "深度学习"。

特点 解释
稳定 同一组 logits 每次都会选同一个 token。
不发散 低分但可能有趣的 token 永远没有机会被选中。
容易重复 长文本生成时可能陷入固定套路，因为每一步都只选局部最高分。

Temperature：调节概率分布的尖锐程度

Temperature 不直接选择 token。它先修改 logits，再 softmax。公式是：

adjusted_logit_i = logit_i / temperature
probability_i = softmax(adjusted_logit_i)
temperature 效果 直观理解
< 1 分布更尖锐 高分 token 更高，低分 token 更低，输出更保守。
= 1 不改变 logits 使用模型原始分布。
> 1 分布更平 低分 token 获得更多机会，输出更发散。

容易误解：temperature 不是“创造力按钮”。它只是改变候选 token 概率的集中程度。模型本身不知道的东西，不会因为 temperature 变高就突然知道。

Top-p：只保留累计概率足够高的一小组候选

Top-p 也叫 nucleus sampling。它不是保留固定数量的 token，而是保留“累计概率达到 p 的最小候选集合”。 

原始概率从高到低排序：
深度学习 0.55
AI       0.25
电影     0.07
音乐     0.05
...

如果 top_p = 0.85：
0.55 + 0.25 = 0.80，还没到 0.85
再加入 0.07，累计 0.87，达到 0.85
所以候选集合保留：深度学习、AI、电影
其他 token 概率置为 0，再重新归一化

Top-p 的作用是切掉概率很低的长尾 token，减少胡乱跳到离谱 token 的机会，同时又保留一定随机性。

Temperature 和 top_p 通常怎么组合

常见顺序是先用 temperature 调整 logits，再 softmax 得到概率，接着做 top_p 过滤，最后从剩余候选中随机抽样。 

adjusted_logits = logits / temperature
probabilities = softmax(adjusted_logits)
filtered_probabilities = top_p_filter(probabilities, top_p)
next_token_id = multinomial_sample(filtered_probabilities)

multinomial_sample 的意思是按概率抽样。概率越高越容易被抽中，但不是最高概率必定被抽中。

max_new_tokens：控制最多生成多少个新 token

max_new_tokens 不改变每一步的概率分布，也不直接控制答案质量。它只是生成循环的上限：最多允许 append 多少个新 token。 

for step in range(max_new_tokens):
    logits = model(input_ids)
    next_token_id = choose_from_logits(logits)
    input_ids.append(next_token_id)
    if next_token_id == eos_token_id:
        break

停止原因 1：达到上限

如果一直没有生成结束符，循环会在达到 max_new_tokens 后强制停止。

停止原因 2：生成结束符

如果模型生成 <eos> 这类结束 token，即使还没达到上限，也可以提前停止。

参数关系总表

参数 / 策略 控制什么 不控制什么
greedy 永远选最高分 token。 不提供随机性，不探索其他候选。
temperature 概率分布尖锐还是平坦。 不限制候选集合大小。
top_p 保留多少累计概率质量。 不直接表示保留几个 token。
max_new_tokens 最多追加多少个新 token。 不保证生成完整句子，也不提高质量。

9. Part 4：KV Cache 为什么能加速生成

KV Cache 解决的是生成阶段的重复计算问题：历史 token 的 Key 和 Value 一旦算出来，后续步骤可以直接复用，不必每生成一个 token 就从头重算整段历史。

先抓结论：KV Cache 不改变模型参数，不改变 attention 的数学含义，也不让模型更聪明。它只是把过去 token 的 K/V 存起来，让推理更快，但会占用更多显存或内存。

运行入口

.venv/bin/python experiments/day-06-llm-inference/kv_cache_shape_demo.py

为什么会有重复计算

自回归生成每次只新增一个 token。假设 prompt 有 4 个 token，要继续生成 3 个 token。如果没有 cache，模型每一步都会把当前完整序列重新送进 Transformer。

生成步 当前序列长度 不用 cache 时会重新计算什么
step 1 4 重新计算 4 个 token 的 Q/K/V 和 attention。
step 2 5 重新计算之前 4 个旧 token + 1 个新 token 的 Q/K/V。
step 3 6 再次重新计算所有历史 token 的 Q/K/V。

这里浪费的地方在于：旧 token 的隐藏向量在当前层中已经确定，它们算出来的 Key / Value 后面不会改变。下一步还把它们重算一遍，就很浪费。

K/V 为什么可以缓存

在 self-attention 中，一个新 token 需要拿自己的 Query 去看所有历史 Key，然后按权重混合对应 Value。

score_new,j = q_new · k_j
attention_weight_new = softmax(score_new)
output_new = sum(attention_weight_new,j * v_j)

对新 token 来说，历史 token 的 k_j 和 v_j 只是被拿来读取。它们不是这一步新算出来的目标，因此可以提前保存。

两次疑问收口：prefill、mask、K/V 到底在做什么

你的问题很关键：如果 prompt 是 "深度学习是什么？"，模型是不是先拿整段序列一起算？如果一起算，为什么又说每个 token 只能看左边？第一位 token 前面没有内容，它的 hidden state 又从哪里来？

推理开始时通常不是一个 token 一个 token 地把 prompt 慢慢送进去，而是先做一次 prefill：把整个 prompt 切成 token 后，一次性形成一个张量。 

tokens = ["深度", "学习", "是", "什么", "？"]
input_vectors.shape = [B, T, D]

B = 1      # batch size，一次处理 1 条 prompt
T = 5      # token 数量
D = 6      # 每个 token 的向量维度，这里只是举例

这 5 个 token 会在矩阵层面一起计算每一层的 Q/K/V。这里的“一起计算”指的是用矩阵并行把所有位置的向量都投影出来，不是让它们随便互相看。真正决定“谁能看谁”的，是后面的 causal mask。 

           被看的 token
           深度   学习    是   什么    ？
正在 深度    看    禁    禁    禁    禁
计算 学习    看    看    禁    禁    禁
的   是      看    看    看    禁    禁
token 什么   看    看    看    看    禁
     ？      看    看    看    看    看

这张表的读法是：每一行代表“正在更新哪个位置的 hidden state”，每一列代表“它可以读取哪个位置的 K/V”。所以第一行的“深度”只能看自己；第二行的“学习”可以看“深度”和自己；最后一行的“？”可以看整个 prompt。

第一位 token 为什么也能得到 hidden state：它至少可以看自己。即使前面没有其他 token，深度 仍然有自己的 token embedding、position embedding、Q/K/V、attention 输出、残差连接、FFN 输出。如果序列前面还有 <BOS> 这类起始符，它还可以看起始符。

常见误区：V 不是“更新后的 hidden state”

你问“mask 之后是不是更新出了每个 token 的 V，然后 KV Cache 缓存这一层的 V”。这里要拆清楚：K 和 V 不是 attention 之后更新出来的结果，而是 attention 之前由当前层输入线性投影出来的中间张量。 

当前层输入 hidden_states
-> Linear_Q 得到 Q
-> Linear_K 得到 K
-> Linear_V 得到 V

attention_scores = Q @ K^T          # 得分来自 Q 和 K，不是 Q 和 V
attention_weights = softmax(mask(attention_scores) / sqrt(d))
context = attention_weights @ V     # 按权重读取 V

updated_hidden_states
= LayerNorm(hidden_states + OutputProjection(context))
-> 再经过 FFN 和残差，得到这一层最终输出

所以 V 更像“可以被读取的内容材料”。真正被更新的是 hidden_states。attention 先用 Q 和 K 算“看谁、看多少”，再用这些权重去混合 V，得到 context。然后 context 经过输出投影、残差连接、归一化和 FFN，才形成新的 hidden state。

对象 它是什么 在 KV Cache 中是否保存
Q 当前 token 用来询问“我应该看谁”的向量。 通常不缓存旧 Q。新 token 只需要自己的 Q。
K 每个历史 token 提供的“可匹配索引”。新 token 的 Q 要和历史 K 做点积，决定注意力分数。 缓存。否则每一步都要重算所有历史 token 的 K。
V 每个历史 token 提供的“可读取内容材料”。权重算好后，会按权重混合这些 V。 缓存。否则权重算好后没有历史内容可读。
hidden_state 当前层真正输出给下一层的 token 表示。 KV Cache 通常不保存完整历史 hidden state。cache 保存的是每层 attention 需要复用的 K/V。

新 token 进来时，每层到底怎么执行

生成出一个新 token 后，下一步 decode 不需要重新更新旧 token。原因是 causal mask 规定旧 token 永远不能看右边未来 token，所以新 token 出现后，旧 token 的历史计算结果不应该被改变。 

# 某一层的 decode 过程，只看一个新 token
new_hidden.shape = [B, 1, D]

q_new = Linear_Q(new_hidden)     # [B, H, 1, d]
k_new = Linear_K(new_hidden)     # [B, H, 1, d]
v_new = Linear_V(new_hidden)     # [B, H, 1, d]

key_cache   = concat(old_key_cache,   k_new, dim=token_dim)
value_cache = concat(old_value_cache, v_new, dim=token_dim)

scores  = q_new @ key_cache.transpose(-2, -1)   # [B, H, 1, T_total]
weights = softmax(scores / sqrt(d), dim=-1)
context = weights @ value_cache                 # [B, H, 1, d]

new_hidden = attention_output_projection(context)
new_hidden = residual_norm_ffn(new_hidden)

这段流程对应你的疑问：新 token 会计算自己的 Q/K/V；它的 Q 马上和缓存里的所有 K 做匹配；匹配得到的权重再去混合缓存里的所有 V。这里不是“拿 Q 去乘 V 算得分”，而是 Q @ K^T 先算分数，weights @ V 再取内容。

两个阶段：prefill 和 decode

Prefill

第一次处理 prompt。模型一次性计算 prompt 中所有 token 的 Q/K/V，并把每层的 K/V 存进 cache。 

prompt length = T
key_cache.shape = [B, H, T, d]
value_cache.shape = [B, H, T, d]

Decode

后续每次只输入最新 token。只为这个新 token 计算 Q/K/V，再把新 K/V 追加到 cache。 

new_query.shape = [B, H, 1, d]
key_cache.shape = [B, H, T_total, d]
scores.shape = [B, H, 1, T_total]

不用 cache vs 使用 cache 的 shape

路径 Q/K/V shape Attention score shape 含义
不用 cache [B, H, S, d] [B, H, S, S] 当前完整序列长度是 S，每步都重算整个序列。
使用 cache 新 token：[B, H, 1, d]
缓存：[B, H, T_total, d]		 [B, H, 1, T_total] 只算新 token 的 Query，让它去看所有缓存的历史 Key。

符号解释

符号 含义
B batch size，一次有几条输入。
H attention head 数量。
S 不用 cache 时，当前完整序列长度。
T_total cache 中已经保存的总 token 数，包括 prompt token 和已经生成的新 token。
d 每个 head 内部的向量维度，通常 d = D / H。

计算量对比：为什么会更快

在 demo 中，prompt 长度是 4，要生成 3 个 token。不用 cache 的路径需要投影的 token 数是： 

4 + 5 + 6 = 15

使用 cache 的路径是先 prefill 4 个 prompt token，然后每个 decode step 只投影 1 个新 token： 

4 + 1 + 1 + 1 = 7

attention score 的数量也从 demo 中的 154 降到 68。真实大模型有很多层、很多 head、长上下文，所以节省会更明显。

KV Cache 的代价

KV Cache 用空间换时间。它要为每一层、每个 head、每个历史 token 保存 Key 和 Value。

cache shape per layer:
key_cache.shape = [B, H, T_total, d]
value_cache.shape = [B, H, T_total, d]

序列越长，cache 越大；batch 越大，cache 也越大。所以 KV Cache 会提升生成速度，但会增加显存占用。

一句话收口：KV Cache 保存的是每层 attention 里历史 token 的 K/V。新 token 仍然要计算自己的 Q/K/V，但它可以直接看缓存里的历史 K/V，从而避免重复计算旧 token。

tokenizer = AutoTokenizer.from_pretrained(model_path)

outputs

模型 forward 的输出。它不是单个 tensor，而是一个带字段的输出对象，里面有 logits 和 past_key_values。

logits

模型对每个位置、每个词表 token 的原始分数表。形状是 [B, T, V]。

10.4 数据流：从 prompt 到下一个 token

prompt 文本
-> tokenizer(prompt, return_tensors="pt")
-> encoded["input_ids"]        # [B, T]，整数 id
-> model(**encoded, use_cache=True)
-> outputs.logits              # [B, T, V]，词表分数
-> logits[:, -1, :]            # [B, V]，最后位置的下一个 token 分数
-> topk / argmax / sampling
-> next_token_id
-> tokenizer.decode(...)
-> 人能读的文本

第一层 看 input_ids.shape = [B, T]，确认 tokenizer 输出的是整数 id。

第二层 看 logits.shape = [B, T, V]，确认每个位置都有一整张词表分数表。

第三层 看 next_token_logits.shape = [B, V]，确认生成时只取最后一个位置。

第四层 看 past_key_values，确认真实模型也在每层保存 K/V。

第五层 看 generate() 输出，把一轮 logits 预测和多轮生成循环连起来。

10.7 问答澄清：mask、padding、batch、上下文窗口

下面是最近两次问题的整理。它们不改变主线，但会决定你是否真的理解真实服务里的输入组织方式。

attention_mask 和 causal mask 不是一回事

mask 解决的问题 例子
attention_mask 告诉模型哪些位置是真 token，哪些位置只是 padding，占位用，不应该参与计算。 [1, 1, 1, 0, 0] 表示前三个是真 token，后两个是 padding。
causal mask 告诉模型当前位置不能看右边未来 token，保证从左到右生成。 第 2 个 token 可以看第 0、1、2 个位置，不能看第 3、4 个位置。

pad_token 是什么

pad_token 是“补齐用 token”。它不是用户真正输入的内容，而是为了把同一个 batch 里的多条序列补到同样长度，方便组成规则张量。 

真实输入 A: "Deep learning is"          -> [29744, 4673, 318]
真实输入 B: "AI is changing the world" -> [20185, 318, 1800, 262, 995]

为了放进同一个 batch，需要补齐到同样长度：
A: [29744, 4673, 318, PAD, PAD]
B: [20185, 318, 1800, 262, 995]

attention_mask:
A: [1, 1, 1, 0, 0]
B: [1, 1, 1, 1, 1]

pad_token 负责补齐形状；attention_mask 负责告诉模型 PAD 位置只是占位，不是真内容。GPT-2 这类模型原本没有专门的 pad token，所以 demo 里临时用 eos_token 充当 pad_token。

batch 里的不同序列会互相看见吗

不会。batch 不是把多句话首尾拼成一条长序列，而是把多条互相独立的输入并排放进同一次计算。Self-Attention 发生在每条序列自己的 T 维度内部，不跨 batch。 

input_ids.shape = [B, T]

B = batch size，几条独立输入
T = 每条输入补齐后的 token 长度

attention_scores.shape = [B, H, T, T]

含义：
第 0 条输入内部算自己的 [H, T, T]
第 1 条输入内部算自己的 [H, T, T]
不同 B 之间不做 attention

商业服务里的 batch 和用户 query 是什么关系

商业级模型服务里，batch 通常包含多个独立请求序列。它们可能来自多个用户，也可能来自同一个用户的多个并发任务。但更准确地说，batch 里放的不是“多个 query 字符串”，而是多个已经整理好的 request sequence。 

一个 request sequence 通常包含：
system prompt
+ developer / tool instructions
+ 历史对话
+ RAG 检索片段
+ 当前用户 query
+ assistant 开始生成前的格式 token

所以一个序列不是单纯的用户 query，而是“当前这次请求真正送进模型的完整上下文”。它的实际长度可以是几百、几千、几万 token，但必须小于或等于模型最大上下文窗口。

概念 准确含义 容易误解的地方
sequence length 当前请求实际送进模型的 token 数。 不等于模型最大上下文，只是这次实际用了多少。
context window 模型最多能接收的 token 数，例如 20k、100k、128k。 这是上限，不代表每次请求都会塞满。
batch 多个独立 request sequence 并行计算。 不是把多个请求拼成一个可互相 attention 的长上下文。

模型并行算完后，每个请求通常取自己最后有效位置的 logits，分别预测自己的下一个 token。A 请求不会看 B 请求，B 请求也不会看 C 请求。

超过最大上下文时，工业界真的会做上下文优化吗

会。你觉得它像智能体上下文优化策略，这个判断是对的，因为它们本质上解决同一个问题：模型一次只能看有限 token，超过了怎么办。

层级 常见处理 说明
模型服务底层 拒绝请求、报错、截断输入、限制最大输入长度。 负责保护模型和推理服务，不保证替你理解全部历史。
应用 / 智能体层 RAG、历史摘要、滑动窗口、长期记忆筛选、上下文压缩。 负责决定哪些信息最值得进入当前 context window。
推理引擎层 continuous batching、paged attention、KV cache block 管理。 负责提高吞吐和显存利用率，不改变“请求之间互相隔离”的原则。

一句话收口：模型本体只能处理有限长度的 token sequence；推理服务把多个独立 sequence 组成 batch 提高吞吐；应用或智能体系统负责决定哪些信息应该进入这个 sequence。

10.8 问答澄清：为什么 tokenizer 词表大小要和 model 匹配

tokenizer 的词表大小决定 token id 的合法范围。模型的 embedding 表和 lm_head 也必须有同样数量的行，才能支持这些 token id。 

tokenizer vocab_size = 50257
model.config.vocab_size = 50257

token_embedding.weight.shape = [50257, hidden_size]
lm_head.weight.shape = [50257, hidden_size]

如果 tokenizer 产生了 token_id = 50000，模型的 embedding 表必须至少有第 50000 行可以查。如果模型只支持 30000 个 token，那么这个 id 就越界了。

反过来，模型输出 logits 时也会输出 V 个分数。第 i 个 logit 的含义必须由同一个 tokenizer 词表解释。如果 tokenizer 和 model 词表不匹配，模型说“我选择第 5087 个 token”，但 tokenizer 可能把 5087 解释成另一个 token，生成文本就乱了。

11. Part 6：真实模型生成参数、停止条件、输出质量

Part 5 已经把真实模型的一轮 forward、logits、KV Cache 和 generate 主线跑通。Part 6 开始看生成控制参数：它们不改变模型权重，但会改变“如何从 logits 选择下一个 token”。

先抓边界：生成参数不是训练参数。它们不会让 tiny-gpt2 变聪明，只会改变候选 token 的选择策略、最多生成多长、什么时候停止。

运行入口

.venv/bin/python experiments/day-06-llm-inference/generation_controls_demo.py

这个脚本使用 tiny GPT-2 做真实生成参数对比。默认仍然是离线 / local-only；如果本机没有模型文件，需要显式加 --allow-download。

generate 参数在生成循环中的位置

repeat:
    outputs = model(input_ids, past_key_values=cache, use_cache=True)
    next_token_logits = outputs.logits[:, -1, :]

    # 生成参数主要作用在这里
    adjusted_logits = repetition_penalty(next_token_logits)
    probabilities = softmax(adjusted_logits / temperature)
    candidate_set = top_k_or_top_p_filter(probabilities)
    next_token_id = greedy_or_sample(candidate_set)

    input_ids = append(input_ids, next_token_id)
    if next_token_id == eos_token_id: stop
    if new_token_count == max_new_tokens: stop

所以你可以把生成参数理解成“最后一步选 token 的规则”。模型 forward 仍然输出 logits；参数决定如何从 logits 里挑下一个 token。

参数总表

参数 控制什么 容易误解的地方
max_new_tokens 最多追加多少个新 token。 不是最终总长度；最终长度约等于 prompt token 数 + new token 数。
do_sample=False 不随机采样，通常每一步选择最高分候选。 稳定，但容易重复，也不探索其他可能输出。
do_sample=True 从概率分布中随机抽样。 不是乱选，仍然受 logits、temperature、top-k、top-p 约束。
temperature 调节概率分布尖锐或平坦。 低温更保守，高温更多样；不是越高越好。
top_k 每步只从概率最高的 k 个候选里采样。 限制的是候选数量，不是累计概率。
top_p 保留累计概率达到 p 的最小候选集合。 候选数量每一步都可能变化。
repetition_penalty 降低已出现 token 再次出现的倾向。 能缓解重复，但不能修复模型知识或推理能力。
eos_token_id 如果模型生成结束符，就提前停止。 模型不一定会主动生成 eos，所以很多时候还是由 max_new_tokens 停止。

Greedy 为什么会重复

在 demo 中，greedy 会不断生成 " factors"。原因不是 generate() 坏了，而是每一步都选择当前最高分 token；tiny-gpt2 很小，分布容易塌到某些高分 token 上。 

do_sample=False
-> 每一步取最高分
-> 如果 " factors" 一直最高
-> 输出就会重复 " factors factors factors"

这说明：确定性生成稳定，但不一定好。模型能力弱、上下文短、重复惩罚不足时，greedy 很容易陷入重复。

Sampling 为什么更随机

do_sample=True 后，模型不再永远取最高分，而是按照概率抽样。temperature、top-k、top-p 都是在塑造“抽样池”。

低温

概率更集中，高分 token 更容易被选中，输出相对保守。

高温

概率更平坦，低分 token 也更容易被抽到，输出更多样但更容易乱。

top-k / top-p

先缩小候选集合，再在集合里采样，避免从整个词表里乱抽。

停止条件如何理解

生成循环必须有停止条件，否则会一直预测下一个 token。当前 demo 主要观察两种停止方式。

停止方式 发生条件 demo 中的表现
max_new_tokens 新生成 token 数达到上限。 tiny-gpt2 通常没有主动生成 eos，所以多数 case 都由这个条件停止。
eos_token_id 模型生成了结束符。 如果生成结果里出现 eos，generate 会提前停止。

为什么参数不能拯救 tiny-gpt2 的输出质量

当前模型的 hidden_size = 2、层数也很少，它是测试模型，不是实用聊天模型。生成参数只能改变“怎么选 token”，不能创造模型权重里没有的语言能力。

一句话收口：模型能力来自训练好的权重；生成参数只是在推理阶段控制选择策略。好模型 + 合理参数，才能得到可用输出。

12. 阶段复盘：LLM 核心链路

这一节整理当前阶段已经学过的关键概念，用来把 tokenizer、embedding、causal Transformer、LM Head 和生成循环连成一条线。

1. Tokenizer 与词表

Tokenizer 是把文本变成 token id 的程序。它通常先在大量语料上独立构建词表和切分规则，然后在 LLM 主模型训练、推理时作为固定的预处理工具使用。

词表如何来

常见算法包括 BPE、WordPiece、Unigram。以 BPE 为例，先从字符或字节开始，再反复统计高频相邻 token 对，把最常见的组合合并成新 token，直到达到目标词表大小。

编码时如何切

推理时使用已经确定的词表和规则。一个容易理解的实现是最长匹配：在当前位置优先匹配最长 token，匹配不到就退回 <unk> 或更细粒度单位。 

for token in tokens_by_length:
    if text.startswith(token, cursor):
        matched_token = token
        break

校准理解：tokenizer 的词表来自统计和规则，不是神经网络里的可学习 embedding 向量。主模型训练时通常不会通过梯度更新 tokenizer 的切分规则。

2. Embedding：token id 变成向量

input_ids 只是整数编号。模型真正计算前，需要用 nn.Embedding 查表，把每个 token id 变成一个连续向量。

token_embedding.weight.shape = [V, C]
input_ids.shape = [B, T]
token_vectors.shape = [B, T, C]

训练开始时，embedding 矩阵通常是随机初始化的。训练过程中，loss 通过反向传播更新这些向量，使模型逐渐学到哪些 token 在语义或用法上更接近。

3. Token Embedding + Position Embedding

token embedding 表示“这个位置是什么 token”；position embedding 表示“这个 token 在第几个位置”。二者相加后，模型输入同时包含内容信息和位置信息。 

model_input = token_vectors + position_vectors

position embedding 可以是可学习参数，也可以是固定规则生成的向量，例如正弦位置编码。当前学习阶段先重点掌握：位置也要变成向量，并和 token 向量合并。

4. Causal Transformer Block

Causal Decoder 的每一层都接收 hidden_states，常见 shape 是 [B, T, C]。经过多层堆叠后，每个位置的向量会融合它自己和左侧上下文的信息。

子模块 作用
LayerNorm 稳定每个 token 向量内部的数值分布。
Q / K / V projection 把每个 token 的隐藏向量投影成 Query、Key、Value，用于计算 self-attention。
Causal Self-Attention 让当前位置只能从自己和左侧 token 聚合信息，不能看未来 token。
Residual 把子层输出加回原路径，保留原始信息并改善深层训练。
FFN Feed Forward Network，逐 token 做非线性加工，不负责 token 间交换信息。

5. Causal Self-Attention 公式

对于位置 t，它先由当前向量产生 q_t，再和所有位置的 k_j 做点积得到分数。mask 会把未来位置 j > t 的分数改成 -inf，使 softmax 后权重变成 0。

q_t = x_t W_Q, k_t = x_t W_K, v_t = x_t W_V
score[t, j] = q_t · k_j
if j > t: score[t, j] = -inf
alpha[t, :] = softmax(score[t, :] / sqrt(d_k))
output_t = sum(alpha[t, j] * v_j, j = 0 到 t)

为什么必须 mask：训练时输入通常是完整序列。如果不禁止未来位置，模型在预测当前位置之后的 token 时会偷看答案。这样训练 loss 会虚低，但推理时因为未来 token 还不存在，模型能力会崩。

6. Hidden States 到 Logits

Transformer 输出的是隐藏向量，不是文字。最后需要 lm_head 把隐藏向量映射到词表空间，让每个候选 token 都得到一个原始分数。

lm_head = nn.Linear(in_features=C, out_features=V, bias=False)
lm_head.weight.shape = [V, C]
logits = hidden_states @ lm_head.weight.T
logits.shape = [B, T, V]

对某一个候选 token i 来说，它的 logit 是最后位置隐藏向量 h 和 lm_head.weight[i] 的点积： 

logits[i] = h · w_i
logits[b, t, i] = sum(hidden_states[b, t, k] * lm_head.weight[i, k])

一些 LLM 会使用 weight tying，也就是让输出层权重和 token embedding 权重共享或绑定。当前阶段只需要先理解：lm_head 的每一行对应词表中的一个候选 token。

7. 推理生成循环

推理时，模型参数已经固定，不再更新。生成不是一次吐出整句，而是不断重复“根据当前序列预测下一个 token”。 

当前 input_ids
-> embedding + position embedding
-> 多层 causal Transformer
-> hidden_states
-> 取最后位置 hidden vector
-> lm_head 得到 next_token_logits
-> softmax / sampling 选择 next_token_id
-> append 到 input_ids
-> 重复直到结束

第一个生成 token 也不是凭空出现的。它至少基于用户 prompt，或者基于特殊起始 token，例如 <BOS>。

8. 关键概念辨析

概念 说明
Tokenizer 把文本切分并映射成 token id 的程序，使用预先构建的词表和规则。
Embedding 模型参数矩阵，把 token id 查表变成连续向量，训练时会被优化。
Causal Mask 让每个位置只能看自己和左侧 token，保证自回归生成。
Hidden State 经过 Transformer 层处理后的 token 向量，编码了当前位置可见上下文。
Logits 候选 token 的原始分数，softmax 前还不是概率。
Autoregressive Generation 基于已生成序列预测下一个 token，再把它拼回去继续预测。
