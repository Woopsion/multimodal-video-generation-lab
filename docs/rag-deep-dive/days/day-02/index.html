01 · Latent document

检索文档 z，为什么叫“隐变量”？

先只理解一个核心关系：用户给出问题 x，系统最后观察到答案 y，但哪一份文档 z 应该支撑这个答案，并不是用户直接标注给模型的输入，而是检索器需要推断的中间变量。

p(y | x) ≈ Σz ∈ top-k pη(z | x) · pθ(y | x, z)
暂时不用推导公式。先读它的结构：检索器给候选文档分配概率，生成器判断在问题与该文档条件下生成答案的概率，两者共同影响最终答案。
DOCUMENT DISTRIBUTION

问题 x：电子产品已经拆封，还能申请退货吗？点击候选文档，观察检索器分配给 z 的权重。

Step 01 最终结论

文档 z 不是用户直接提供的已知输入，而是检索器根据问题 x 从文档空间中推断的概率分布。正确文档概率过低时，它可能掉出 top-k 或贡献过小；生成模型再强，也只能围绕错误或不足的证据回答，结果往往“看起来合理但没有回答到点子上”。

02 · Marginalization granularity

RAG-Sequence 与 RAG-Token，差异不在“检索几次”

两者都把候选文档 z 当作隐变量。真正的差异是：对 z 的求和发生在整段答案概率之外，还是发生在每个 token 的生成概率之内。

RAG-Sequence · 对整段答案进行边际化

pseq(y | x) ≈ Σz ∈ top-k(x) pη(z | x) · ∏i=1N pθ(yi | x, z, y<i)

读法：先假设同一份候选文档 z 支撑完整答案的全部 token，算出这条完整答案路径的概率；再把每份候选文档的路径贡献加起来。

RAG-Token · 对每一个 token 进行边际化

ptok(y | x) ≈ ∏i=1N Σz ∈ top-k(x) pη(z | x) · pθ(yi | x, z, y<i)

读法：生成第 i 个 token 时，先把各候选文档对这个 token的贡献加起来；然后再把所有 token 的概率连乘。它不表示每个 token 都重新发起一次检索。

把公式拆成 6 个可读符号

这里的 top-k(x) 是简写：检索器按 pη(z | x) 排名后保留下来的 k 份候选文档。

x

用户问题（query）。

y = (y₁, …, yN)

最终答案；生成器按 token 自回归地产生它。

z

候选检索文档，也是本节讨论的隐变量。

pη(z | x)

检索器认为文档 z 与问题 x 相关的概率或权重。

pθ(yi | x, z, y<i)

给定问题、文档与已生成前文后，生成第 i 个 token 的概率。

Σ / Π / ≈

Σ 是“对文档贡献求和”，Π 是“按 token 概率连乘”；≈ 是因为工程上只在 top-k 候选中近似求和，而非枚举全库。

Generation timeline

观察文档贡献在生成过程中的位置

先抓住括号位置。Sequence 是“每个候选文档分别解释完整答案，再对完整答案概率求和”；Token 是“每生成一个 token，都先对候选文档的贡献求和”。后者更灵活，但计算与解释都更复杂，也更容易在长答案中混合不同证据路径。
Step 02 最终复述
你的原始判断

“显然是 RAG-Token，因为最终生成的 y 的内容要综合结合检索出的 z₁、z₂ 文档的相关内容。”

完善后的表述：RAG-Token 更容易让答案不同部分受到不同文档影响。对第 i 个 token，它先对 z₁、z₂ 等候选文档的生成贡献求和；因此“退货条件”对应的 token 可以主要由 z₁ 支撑，“会员补贴”对应的 token 可以主要由 z₂ 支撑。

关键限定：RAG-Sequence 不是“只检索一篇文档”。它仍会对候选文档的完整答案路径求和；但在任意一条完整路径内部，同一份 z 要解释整段答案，所以跨文档分工的灵活性更低。

Step 02 已收口

03 · Offline indexing / first boundary

索引保存的不是“整份文档”，而是可检索记录

一份 PDF、网页或制度文档只是知识来源。在线检索真正返回的，通常是由正文片段、向量表示和 metadata 共同构成的逻辑记录。今天先只看清这次形态变化。

先建立一条边界。离线阶段决定“未来能被检索到的最小证据单元”。原文中存在某条知识，不等于这条知识一定以完整、可定位、可召回的形式进入了索引。

Document transformation

切换观察：知识源与检索单元不是同一个对象

这一轮只记住一句话

RAG 检索的直接对象通常不是原始 PDF，而是离线阶段构造出的 chunk 记录；embedding 用于相似度搜索，正文用于提供证据，metadata 用于过滤、权限和追溯。它们在物理存储上可以分开，但在逻辑上共同描述一个可检索单元。

Step 03 已收口

原文连续写着“已经拆封仍可退货，但仅限签收后 7 天内”。如果切分后，前半句与“7 天”落在两个不同 chunk，而在线检索只召回前一个 chunk，生成器最可能缺少什么？这首先属于检索阶段的问题，还是生成阶段的问题？

标准复述

生成器缺少的是“签收后 7 天内”这一关键约束。问题首先出现在证据链路：正确知识虽然存在于原文甚至索引中，但没有进入本次召回结果，生成器拿到的是不完整证据。

更精确地说，现象属于召回/上下文缺失；根因可能来自离线切分，也可能来自在线排序与 top-k 设置。不能先把责任归给生成模型。

04 · Online retrieval and generation / first boundary

检索到了，不等于模型最终看到了

在线问答不是简单的“检索 → 生成”两步。候选文档被召回以后，系统还会过滤、截断、去重和排序，再组装成真正送给生成模型的 context。

先分清两个集合。retrieved candidates 是检索器返回的候选集合；final context 是上下文构造器最终交给模型的证据集合。正确 chunk 可以出现在前者，却消失在后者。
这一轮只建立一个诊断边界

检索器负责“哪些候选有机会进入答案”，上下文构造器负责“哪些证据真正进入模型输入”。评估 RAG 时必须分别观察 retrieved top-k 与 final context，不能只看最终答案。

Completed checkpoint

Step 04 已收口

包含“7 天退货期限”的 chunk 排在检索结果第 4 名，检索器返回 top-5；但上下文构造器因为 token 预算只保留前 3 名。此时检索是否成功？最应该先检查或调整哪个环节？

标准复述

以 candidate recall 为边界，检索已经成功：正确 chunk 位于返回的 top-5。证据随后被上下文构造器按 token 预算截断，因此应先检查 context selection、重排顺序和预算分配，而不是先更换 embedding 模型。

这说明必须分别记录 retrieved candidates 与 final context。只观察最终 prompt，会误以为检索器从未找回正确证据。

05 · Decision map / first synthesis

把 RAG 管道变成 8 个可诊断的工程决策点

专家式理解不是背组件名，而是知道每个边界做了什么选择、留下什么产物、应该用什么信号验证。先把离线与在线决策分组观察，再完成最后一次综合判断。

决策点不等于默认参数。一个可维护的决策点至少包含：选择依据、版本或配置、输入输出样本，以及能够判断它是否失效的指标。

Eight decision points

Day 02 最终复述

原始 RAG 把检索文档 z 看作隐变量：检索器用 pη(z|x) 给候选证据分配权重，生成器用 pθ(y|x,z) 判断在问题和证据条件下生成答案的概率。RAG-Sequence 在一条完整答案路径内固定同一份 z，再对文档路径求和；RAG-Token 则在每个 token 位置对文档贡献求和，因此能更灵活地混合多份证据。

工程实现分为离线索引和在线问答。离线阶段把原始资料解析、切分、编码并写成可检索记录；chunk 正文提供证据，embedding 用于相似度检索，metadata 支撑过滤、权限和追溯。在线阶段依次完成 query 构造、候选召回、context 组装和答案生成。retrieved candidates 与 final context 必须分开观察，因为正确证据可能已被召回，却在重排、过滤或 token 截断时消失。

排障时不应先换大模型，而应沿证据链逐层定位：先确认最新知识是否进入索引，再检查正确 chunk 是否进入 top-k，然后检查它是否进入 final context；只有证据完整而模型仍误读或违背约束时，才更接近生成失败。

Day 02 completed

最后一次判断已收口

退货政策已从“7 天”更新为“15 天”，但系统仍回答 7 天。为了最快区分“索引没更新”和“在线链路选错证据”，你会优先对比哪两类中间产物？

标准诊断答案

第一类是离线索引中的最新可检索记录：检查 15 天政策对应的 chunk 正文、版本和更新时间，证明新知识是否已经被解析并写入索引。第二类是本次在线请求的证据轨迹：对比 retrieved top-k 与 final context，证明系统召回并最终交给模型的是 15 天新证据，还是 7 天旧证据。

若索引中只有 7 天，根因在数据更新或索引生命周期；若索引已有 15 天但 top-k 没有它，检查 query、过滤、embedding 与排序；若 top-k 有而 final context 没有，检查重排、去重与 token 预算；若 final context 已有 15 天却仍回答 7 天，再检查生成约束和模型忠实度。

面试版表达

我会把 RAG 看成一条可观测的证据供应链，而不只是“向量库加大模型”。离线侧决定知识能否以正确粒度进入索引，在线侧决定正确证据能否经过召回和上下文构造真正到达生成模型。遇到错误答案时，我会按 indexed record → retrieved top-k → final context → answer 的顺序比较中间产物，从而区分索引陈旧、召回失败、上下文丢失和生成失败。
