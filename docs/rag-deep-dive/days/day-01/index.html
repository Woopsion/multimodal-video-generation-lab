Step 01 · Mental Model

RAG 不是“接一个向量库”

先从最简单的信息流出发。用户提出问题后，系统需要从外部知识中找到足够回答问题的证据，再把证据交给模型组织答案。

RAG 的核心任务，是让最终上下文中的证据 z 尽可能成为回答问题 x 所需的最小充分证据集。
INPUT用户问题 x

用户真正想知道什么？

SEARCH寻找候选证据

从外部知识中缩小范围。

SELECT形成证据 z

保留相关且足够的内容。

GENERATE模型组织答案

依据问题与证据进行表达。

OUTPUT答案 y

附引用、边界或拒答。

没有 RAG 时，模型主要依靠训练阶段写入参数的知识生成答案。加入 RAG 后，回答条件从“问题”扩展为“问题 + 当前检索到的证据”。因此，知识可以在不重新训练模型的情况下更新、撤回、引用和做权限过滤。

选读：用概率形式描述这个变化
p(y | x) → p(y | x, z)

x 是问题，z 是检索证据，y 是答案。这个公式不是要求今天推导，而是提醒我们：RAG 的所有组件最终都在影响证据 z 的质量。

Step 02 · Decision Boundary

RAG、微调和长上下文管理的是不同问题

不要把它们理解成互相替代的三种模型技巧。点击下面三个场景，观察每种方案最适合管理什么。

Scenario explorer

需求发生变化时，应该改变哪一层？

优先考虑RAG

企业制度、产品说明和用户数据会持续变化，而且需要引用来源、删除旧版本并执行文档权限。

  • 知识更新通常只需要更新索引。
  • 答案可以回到原始文档进行审计。
  • 访问控制可以在检索层强制执行。
优先考虑微调

目标是让模型稳定遵循公司的表达方式、输出固定 JSON、掌握任务步骤或形成领域行为习惯。

  • 微调更擅长改变“如何回答”。
  • 它不适合频繁注入需要实时更新的事实。
  • 真实系统常采用“微调管行为，RAG 管知识”。
优先考虑长上下文

用户临时上传一份合同或一组资料，本次任务需要整体分析，而且材料规模可控。

  • 资料只服务当前请求，不一定值得长期建库。
  • 材料过多时会增加 token 成本和延迟。
  • 长上下文并不自动解决信息筛选和中间位置利用率问题。

三者可以组合：RAG 管理动态知识，微调管理稳定行为，长上下文承载单次任务资料。真正的选型依据是知识是否变化、是否需要引用和权限、任务是否重复，以及成本与延迟约束。

Step 03 · Failure Map

先判断证据在哪里，再讨论谁出了问题

“回答错了”不是一个足够具体的诊断。先确认正确证据是否进入了模型最终看到的上下文，再决定进入检索侧还是生成侧。

Trace explorer

切换两种坏案例，观察第一检查点

01数据 / ACL
02解析 / 分块
03召回 / 重排
04最终上下文
05答案生成
先查检索链路

依次确认文档存在、解析没有丢失、chunk 保留了必要上下文、初次召回命中，以及融合/重排没有把证据丢掉。

再查生成链路

确认没有被截断，再观察 chunk 数量、证据位置、指令冲突、引用约束和模型是否能准确摘录证据。

因此，Lost in the Middle 不是每次的默认答案。它只是“证据已经进入上下文，但模型没有有效使用”这一类生成问题中的一种可能原因。检索失败和生成失败要靠 trace 分层，而不是凭感觉更换模型。

把排查顺序记成一句话
数据存在？ → 正确解析？ → 初次召回？ → 重排保留？ → 最终上下文？ → 模型使用？

Step 04 · Personal Synthesis

Day 01 最终复述

下面保留的是基于本次讨论修正后的版本。它既是学习记录，也可以继续压缩成面试时的 3 分钟表达。

选型顺序：动态事实、引用与权限优先考虑 RAG；稳定行为与格式优先考虑微调；单次已知资料优先考虑长上下文，并允许三者组合。
  • 关键修正 01：检索失败不只是“召回了无关内容”，而是正确证据没有进入最终上下文。
  • 关键修正 02：生成失败的前提是正确证据已经进入上下文，但模型没有正确使用。
  • 关键修正 03：Lost in the Middle 需要在确认上下文和证据位置后再验证，不能作为第一反应。
