01 · PDF is a drawing program

人看见“页面结构”，解析器首先看见坐标与绘制对象

文本型 PDF 通常保存字符及其页面坐标，但不一定保存标题、段落、双栏阅读顺序或表格单元格等语义结构；扫描型 PDF 甚至可能只有页面图像。

关键边界：“页面上能看见正确内容”不代表“抽取结果保留了正确语义”。如果阅读顺序、表格关系或字符本身在解析时丢失，后面的 chunk、embedding 和生成模型只能处理被破坏后的证据。

Same page / three representations

同一页技术手册，进入系统后可能变成什么

这一轮只记住一句话

解析不是把 PDF “另存为文本”，而是从字符坐标、绘制对象或页面图像中重建阅读顺序和语义结构。解析错误是上游证据损坏，不应先归因给向量模型。

Completed checkpoint

Step 01 已收口：先定位证据在哪一层被破坏

一页设备手册左栏写“故障原因”，右栏写“处理动作”，下方表格把错误码 E42 对应到“重启模块”。朴素抽取后双栏内容交错，表格又变成连续字符串。此时最先损坏的是什么信息？这首先是解析失败、检索失败，还是生成失败？

纠正与补全

最先丢失的是双栏的阅读顺序、栏位归属，以及表格中“错误码 → 处理动作”的单元格关系。字符可能仍然全部存在，但证据之间的关系已经错误，因此第一处失败属于解析失败。检索不准或生成答错可以成为它的下游结果，却不是这条链路最早的根因。

面试表达

我会先检查解析产物，而不是先换 embedding。只要阅读顺序或表格关系在索引前已经损坏，后续检索器只能召回错误组织的 chunk，再强的生成模型也无法稳定恢复原始证据关系。

02 · Structure recovery

解析器的交付物不应只是一串字符，而应是一组带关系的文档对象

结构恢复的目标不是复刻页面样式，而是保存那些会影响检索、分块、引用和权限判断的语义关系。后续 chunker 应消费结构化 block tree，而不是已经被压平的全文字符串。

最小结构合同：每个内容块至少要回答“我是什么类型、我属于哪个章节、我和谁存在关系、我来自哪里”。阅读顺序决定内容如何串联，标题层级决定语境，表格与图注关系决定事实含义，页码和坐标保证答案可追溯。

Structure inspector

同一页内容，解析器需要恢复四类信息

结构恢复与分块的边界

解析器负责把页面恢复成有类型、有顺序、有父子关系和来源坐标的 blocks；分块器再依据问题与检索需求，把这些 blocks 组合成证据单元。若先压平再切分，chunk size 调得再精细也无法重建已经消失的关系。

Completed checkpoint

Step 02 已收口：让解析结果成为可验证的结构合同

技术手册中，标题路径是“故障处理 > 通信模块”，表格一行是“E42｜通信异常｜重启模块”，它位于第 7 页。若后续系统需要准确检索并引用这条处理规则，解析器至少应保留哪些结构或关系？

解析器最小结构合同

内容层保留 block_type、text 与 reading_order；上下文层保留 section_path 或父子 block；关系层保留表头、行列、单元格角色和同一行关联；来源层保留 source_id、版本、页码与 bbox。表格还应序列化为“错误码 E42，原因是通信异常，处理动作为重启模块”这样的自包含证据，不能只保存三个相邻字符串。

面试表达

解析器的输出应该是一棵带来源坐标的 block tree，而不是纯文本。结构路径帮助短 chunk 保留主题，关系信息保护表格与图注含义，来源字段支撑引用、权限、增量更新和解析回归测试。

03 · Three granularities

最容易被召回的片段，不一定是完整证据；完整证据也不等于最终上下文

一个固定 chunk 同时承担向量匹配、事实表达和生成上下文，往往会让三个目标互相牺牲。成熟系统会把索引单元、证据边界与上下文扩展分开设计。

检索单元 ≠ 原子证据 ≠ 最终生成上下文
关键设计：可以用较小的 child chunk 做精准召回，但命中后沿 parent_id、标题路径或相邻关系扩展出完整证据，再由上下文构造器在 token 预算内组合最终输入。这通常被称为 small-to-big 或 parent-child retrieval。

One source / three lenses

同一条退货规则，在链路中需要三种范围

不要把“切多大”当成孤立问题

粒度选择同时受查询分布、事实跨度、文档结构和生成预算影响。小块提高局部匹配的辨识度，大块保留更多条件与上下文；把召回和扩展分成两步，才能避免二选一。

Completed checkpoint

Step 03 已收口：让不同范围承担不同职责

用户问“已拆封的定制商品能否退货？”检索器命中了 child chunk“已拆封商品可以退货”，但同一父章节的相邻证据写着“仅限签收后 7 天内，定制商品除外”。你会让索引/召回单元和最终生成上下文分别包含什么？为什么不直接把所有 chunk 统一调大？

纠正与补全

索引侧可以保留聚焦的 child chunk，提高“拆封 + 退货”的局部匹配能力；命中后必须沿 parent_id 或相邻关系扩展，把“7 天限制”和“定制商品除外”纳入完整证据；最终上下文只组合这组充分证据和来源信息，不必带入退款到账等无关段落。统一放大所有 chunk 会稀释向量主题、增加近似候选和 token 成本，也无法适配不同事实跨度。

与 GraphRAG 的边界

这里遍历的是父子块、标题路径和相邻块，属于 hierarchical RAG 或 small-to-big retrieval。它确实具有图结构，但边来自文档结构；GraphRAG 通常进一步抽取实体与语义关系，并进行多跳子图或社区级检索。

Step 04 已收口：基线参数只是系统决策的一部分

上表来自同一客服政策评测集。你会选择哪个 chunk size 作为第一版基线？如何处理少数证据跨度超过该基线的长尾问题？请说明你接受了什么代价，而不是只回答一个数字。

基线与代价

320 tokens 是这个示例数据上的合理第一版基线，不是普适常数。相对 160，它接受 Recall@5 下降 0.03、Top-5 正文成本翻倍，以换取条件题正确率从 0.70 提升到 0.87；相对 640，它接受正确率下降 0.02，以换取 Recall@5 提升 0.10 且上下文成本减半。

必须修正的边界：系统不能只看 query 就准确预知答案跨几个 chunk。固定扩展、条件扩展和 parent-child 都只是局部证据补全策略；当证据跨章节、跨文档或需要多跳关系时，它们不是完整解决方案，更不能被包装成“自动解决长尾证据”。

From local tactic to adaptive retrieval

01 / PLAN拆解信息需求

识别局部事实、条件例外、比较、多跳和时间版本问题。

02 / RECALL多粒度混合召回

联合 BM25、dense passage、章节、表格和实体索引生成候选。

03 / WORKSPACE证据工作区

重排、去重并记录每个子问题已经获得的支持证据。

04 / CHECK充分性检查

找出仍未被支持的条件、比较项或关系，而非盲目扩大邻居。

05 / LOOP有界重试或拒答

针对缺口再检索 1-2 轮；仍不足时明确缺失信息并拒答。

工程结论

Parent-child 应作为候选召回内部的一个算子，而不是整个系统的智能来源。跨文档隐式关系可进一步使用实体/关系索引、GraphRAG 或迭代检索；这些方案仍有规划错误、延迟、成本和充分性误判，因此必须限制轮数、保留中间产物并支持拒答。

05 · Failure matrix

失败样例必须定位到第一处损坏的中间产物，才能变成回归测试

“答案错了”不是可执行诊断。每个失败样例都应记录文档形态、可见症状、第一处错误产物、责任层、修复策略和能够自动判定是否复发的断言。

诊断原则：沿 source → parsed blocks → structured blocks → indexed records → retrieved candidates → final context 顺序检查。一旦找到第一处错误，后续错误都先视为传播结果。

Step 05 已收口：把错误答案改写成可复现的工程契约

你已经完成了一个失败样例的诊断。现在它不再只是“某次回答错了”，而是一个可反复执行的输入、断言与预期行为。

参考答案：什么才叫可测试

一个合格样例应写成 input document + query → expected first broken artifact → expected evidence set / invariant → expected answer behavior。例如扫描 PDF 中 E42 被 OCR 成 E4Z：第一处错误是带 page、bbox 与 confidence 的 OCR block，而不是 embedding；修复可包括图像校正、领域错误码词表/正则校验、低置信度复核，并保留原图与坐标；回归要同时断言错误码精确为 E42、低置信度不允许静默发布索引、查询 E42 能召回自包含的表格行。

分层断言

解析/结构缺陷断言 parsed blocks、结构化表格行或标题路径；分块缺陷断言标注证据是否完整覆盖，而不是只看最终答案；检索架构缺陷断言查询计划、gold evidence 覆盖、有界重试与拒答出口。每层都应该在生成模型之前暴露问题。

面试表达

我不会从最终错误答案倒推猜 embedding 或 prompt；我会沿 trace 找到第一处损坏的中间产物，并把它固化为回归测试。这样一次坏案例才会变成可验证的工程改进。

文档解析与分块决定 RAG 的证据上限。PDF 和扫描件不是天然语义文本，解析器应交付带类型、顺序、层级、关系和来源的 block tree；检索 child、完整证据和最终上下文也不应由同一个固定 chunk 承担。chunk size 要在真实问题分布上用评测选择，而 parent-child 只适合补局部结构证据。面对跨文档或多跳问题，我会用查询规划、多索引召回、重排和充分性检查做有界迭代；证据仍不足时拒答。排障时沿 trace 找第一处错误，并把坏案例固化成回归测试。
