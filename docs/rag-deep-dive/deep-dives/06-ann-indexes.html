ANN 索引彻底讲透：
用真实数字和可跑代码理解 IVF、PQ、HNSW

主文档 §5.1 的表格告诉你三大索引家族"是什么"；本文用一个贯穿全文的具体设定 （100 万条 768 维向量的知识库）把每种索引的内存、计算量、参数都算出真实数字， 并给出可直接运行的 FAISS 代码——读完你能回答"为什么快、快多少、精度亏在哪、参数怎么调"。

A基线：暴力检索到底有多贵（先建立数字感）

全文使用统一设定：N = 100 万个文档切片，d = 768 维 float32 向量（BERT-base 输出维度）。所有后续对比都相对这个基线。

存储：1,000,000 × 768 维 × 4 字节(float32) = 3,072,000,000 B ≈ 2.86 GB 单次查询计算（暴力精确检索 Flat）： 每个内积 = 768 次乘加 → 全库 = 10⁶ × 768 ≈ 7.7 × 10⁸ 次浮点运算 单核 CPU（~10 GFLOPS 实效）：约 70-100 ms/查询；再加 top-k 堆维护 → 单机单核 QPS ≈ 10；上到 1 亿向量则单查询数秒，彻底不可用
  • 暴力检索（FAISS 的 IndexFlatIP）是100% 召回的金标准——所有 ANN 索引的"召回率"都是拿它当分母算的：recall@10 = ANN 返回的 top-10 里有几个出现在暴力检索的真 top-10 里。
  • <10 万向量时暴力检索毫秒级即可完成，根本不需要 ANN——这是"小项目直接用 numpy 点积"合理的原因，也是选型第一问是"规模多大"的原因。
ANN 的本质一句话

所有 ANN 索引都在做同一件事：预先给向量空间建立某种"地理结构"（簇、图、码本），查询时利用结构跳过绝大多数不可能是答案的区域。三大家族的区别只是"地理结构"长什么样：IVF 是行政区划，HNSW 是高速公路网，PQ 是有损压缩的地图缩略图。代价都一样：真答案可能恰好在被跳过的区域里——这就是"近似"二字的全部含义。

BIVF：先分区、再只搜几个区

B.1 离线建索引：k-means 划分行政区

① 训练：对（抽样的）向量跑 k-means，聚成 nlist 个簇 设 nlist = 1024 → 得到 1024 个"簇中心"向量（centroid） 直觉：中心 #17 可能落在"中国历史"语义区，#301 落在"体育赛事"语义区 ② 分配：每个向量归入最近的簇中心，建立倒排表（inverted lists） 倒排表[17] = [切片id_204, 切片id_88931, ...] ← 平均每簇 10⁶/1024 ≈ 977 条 倒排表[301] = [...] （"IVF" = InVerted File，名字就来自这个倒排结构）

B.2 在线查询：粗排 + 细排两级

① 粗排：query 向量 q 与 1024 个簇中心算内积 → 选最近的 nprobe 个簇 设 nprobe = 8 → 计算量 1024 × 768 ≈ 7.9 × 10⁵ 次乘加 ② 细排：只在这 8 个簇的倒排表内做精确内积 候选量 ≈ 8 × 977 ≈ 7,800 条 → 7800 × 768 ≈ 6.0 × 10⁶ 次乘加 总计算量 ≈ 6.8 × 10⁶ vs 暴力的 7.7 × 10⁸ → 约 113 倍加速 实测召回率（典型文本 embedding 分布）：recall@10 ≈ 90-95%

B.3 精度亏在哪：边界问题

真最近邻可能恰好落在没被探查的邻簇里——尤其当 q 落在两簇边界附近时（q 离中心 A 稍近，但真答案被划进了中心 B 的倒排表）。这就是 IVF 唯一的、也是根本的误差来源。两个应对：

  • 调大 nprobe：nprobe 从 8 → 32，召回率上升、延迟近似线性增加。nprobe = nlist 时退化为暴力检索（100% 召回）。nprobe 就是 IVF 的"召回-延迟"旋钮。
  • 经验参数：nlist ≈ 4√N ~ 16√N（N=10⁶ 时约 4096~16384 也常见；本文取 1024 便于算数），k-means 训练样本至少 30×nlist 条。
IVF 特有的运维坑

簇中心是按建索引当时的数据分布训练的。若语料随时间漂移（新领域文档大量涌入），新向量会挤在少数簇里（倒排表长度失衡），召回率静默下降——需要周期性用新数据重训簇中心并重建索引。HNSW 无此问题（增量插入天然适应分布），这是两者选型的重要差异点。

CPQ 乘积量化：把 3072 字节压成 96 字节

IVF 解决"算得多"，PQ 解决"存得大"。它是三大件里最数学的一个，但用具体字节数算一遍就透了。

C.1 机理：分段 + 每段查字典

① 切段：768 维向量切成 m = 96 段，每段 8 维 v = [v₁…v₈ | v₉…v₁₆ | … ] → 96 个 8 维子向量 ② 每段独立训练一个 256 词的"码本"（codebook）： 对全库所有向量的"第 1 段"跑 k-means(k=256) → 得到 256 个 8 维聚类中心 …对 96 段各做一次 → 96 本字典，每本 256 个词 ③ 编码：每个子向量用"最近的码本中心的编号"代替 8 维 float32 子向量（32 字节） → 1 个字节（0~255 的编号） 压缩效果：768 × 4 = 3072 字节 → 96 字节，压缩 32 倍 全库存储：2.86 GB → 91.6 MB（外加码本本身：96 × 256 × 8 × 4B ≈ 786 KB，可忽略）

C.2 查询时怎么算距离：ADC 查表法（真正的精妙处）

查询 q 来了（q 不量化，保持精确）： ① 预计算查找表：q 的第 s 段与该段码本的 256 个中心逐一算距离 → 96 段 × 256 项 = 24,576 个距离值，存成表 LUT[s][c]（一次性，~2万次运算） ② 之后每条候选向量的"距离"= 96 次查表相加（不再做任何乘法！） dist(q, v) ≈ Σ_{s=1..96} LUT[s][ code_v[s] ] 对比：精确内积 768 次乘加 → PQ 近似距离 96 次查表加法，且缓存友好

这个技巧叫 ADC（Asymmetric Distance Computation，非对称：query 精确、库向量量化）。它让 PQ 不只是省内存——距离计算本身也快了近一个数量级。

C.3 精度亏在哪，怎么补

  • 误差来源：每个子向量被"吸附"到最近的码本中心，量化残差直接进入距离估计。压得越狠（m 越小 / 每段维度越高）误差越大。
  • 标准补救：refine 重打分。用 PQ 距离粗筛 top-100，再对这 100 条读原始 float32 向量算精确内积重排出 top-10。原始向量可以放磁盘（只随机读 100 条，代价极低）——"量化粗筛 + 原始重排"是生产标配（FAISS 的 IndexRefineFlat、Qdrant 的 rescoring 都是它）。
  • 更温和的量化：SQ（标量量化，float32→int8，压 4 倍，精度损失极小，Qdrant/Milvus 默认可开）；更极端的：BQ（二值化，每维 1 bit，压 32 倍，配合汉明距离，靠 refine 兜底）。

DHNSW：可导航小世界图（今天的默认答案）

D.1 一层的情况：在近邻图上贪心游走

把每个向量看作图上一个节点，与它最近的 M 个邻居连边。查询 = 从任一入口点出发，贪心游走：每步跳到"当前节点的邻居中离 q 最近的那个"，直到没有更近的邻居。问题：单层近邻图全是"短边"，从入口走到目标要跳很多步，且容易困在局部最优（当前点的所有邻居都不更近，但真答案在两步之外）。

D.2 多层结构：skip-list 的图版本

Layer 2（约 1/万 的点） ●─────────────● ← 超长边："跨省高速" │ │ Layer 1（约 1/百 的点） ●────●────────●─────● ← 中等边："省道" │ │ │ │ Layer 0（全部 100 万点） ●─●──●──●──●──●──●──●──● ← 短边："街道"，真正的答案层 查询：从顶层入口贪心游走到该层局部最近 → 降一层继续 → … → 到 Layer 0 用宽度为 efSearch 的候选队列做束搜索，返回 top-k 每个点的层数按几何分布随机抽定（多数点只在 L0，极少数点"长"到高层）
  • 高层长边负责"跳远"（快速逼近目标区域），底层短边负责"精确逼近"——与 skip-list 的多级索引完全同构，查询复杂度 O(log N)。
  • 真实数字：100 万向量、M=16、efSearch=64 时，单查询典型只访问几千个节点（vs 暴力 100 万），CPU 上 1-5 ms，recall@10 常见 > 98%——这就是它成为几乎所有向量库默认索引的原因。

D.3 三个参数的真实语义

参数语义调大后果典型值
M每个节点在每层的连边数上限图更稠密：召回↑、内存↑（边表 ∝ M）、建图慢16~48
efConstruction建图时为每个新点找邻居的搜索宽度图质量↑（边选得更准）、建图时间↑；只付一次成本，建议舍得给（200~400）200
efSearch查询时候选队列宽度召回↑、延迟↑。这是线上唯一需要动态调的旋钮，与 IVF 的 nprobe 地位等价50~200

D.4 内存账单与两个结构性弱点

HNSW 内存 ≈ 原始向量 + 边表 = 2.86 GB + 10⁶ × M × ~8B（M=32 时边表 ≈ 0.26 GB，还有高层等开销） ≈ 3.2 GB —— 必须全部驻留内存（图游走是随机访问，放磁盘会被 IO 杀死）
  • 弱点一：全内存驻留。亿级向量 × 高维 = 数百 GB RAM，单机撑不住。解法：PQ 压向量 + HNSW 建图（各库的 "HNSW-PQ"）、或换 DiskANN（Vamana 图 + 压缩向量驻内存导航 + 原始向量放 SSD refine，十亿级单机的标准答案）。
  • 弱点二：删除是软删除。从图里真删一个节点会破坏连通性，只能打标记（查询时跳过），删多了图质量退化 → 需要周期性重建。这与主文档 §13.1"索引的生命周期"直接相关。

E可跑实例：FAISS 上把三种索引跑出对比数字

# uv add faiss-cpu numpy
import faiss, numpy as np, time

d, N = 768, 1_000_000
xb = np.random.randn(N, d).astype("float32")   # 库向量（演示用随机；真实场景换成 embedding）
xq = np.random.randn(100, d).astype("float32") # 100 条查询
faiss.normalize_L2(xb); faiss.normalize_L2(xq)   # 归一化后内积 = 余弦（主文档 §4.2）

# ① 暴力精确：金标准，用它的结果算其他索引的召回率
flat = faiss.IndexFlatIP(d); flat.add(xb)
_, gt = flat.search(xq, 10)                      # ground truth top-10

# ② IVF+PQ：nlist=1024 个簇，PQ 96 段每段 8bit
ivfpq = faiss.index_factory(d, "IVF1024,PQ96x8", faiss.METRIC_INNER_PRODUCT)
ivfpq.train(xb[:200_000])                        # 训练簇中心 + PQ 码本（抽样即可）
ivfpq.add(xb)
ivfpq.nprobe = 8                                 # 召回-延迟旋钮①

# ③ HNSW：M=32
hnsw = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)
hnsw.hnsw.efConstruction = 200
hnsw.add(xb)                                     # 建图较慢（分钟级），一次性成本
hnsw.hnsw.efSearch = 64                          # 召回-延迟旋钮②

def bench(name, index):
    t0 = time.perf_counter()
    _, ids = index.search(xq, 10)
    ms = (time.perf_counter() - t0) / len(xq) * 1000
    recall = np.mean([len(set(a) & set(b)) / 10 for a, b in zip(ids, gt)])
    print(f"{name:10s}  recall@10={recall:.3f}  {ms:.2f} ms/query")

bench("Flat", flat); bench("IVF-PQ", ivfpq); bench("HNSW", hnsw)

# 典型输出形态（数值随机器浮动）：
#   Flat        recall@10=1.000   ~80 ms/query      ← 精确但慢
#   IVF-PQ      recall@10=0.85~   ~0.3 ms/query     ← 快 + 省内存(96B/向量)，精度换的
#   HNSW        recall@10=0.98~   ~0.5 ms/query     ← 快 + 高召回，内存换的
动手实验建议（做完这两个实验，三角权衡就长在直觉里了）
  • 把 nprobe 从 1 扫到 64、efSearch 从 16 扫到 256，画"召回率-延迟"曲线——你会亲眼看到两个旋钮的边际收益递减点。
  • 注意随机高斯向量是 ANN 的最难情况（无簇结构、维度灾难拉满）；换成真实 embedding（有语义簇）后所有索引的召回率都会明显更好。这个对比本身就是对"数据分布决定索引表现"的最好演示。
