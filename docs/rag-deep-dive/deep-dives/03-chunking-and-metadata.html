分块策略：逐个拆解、前沿进展与 Metadata 设计

主文档的谱系表是"地图"，本文是每个地点的"街景"：每种策略讲清机制细节、参数、失败模式、何时选它； 然后回答"为什么主流方法停在 2024"，并盘点 2025 以来的真实前沿；最后把 Metadata 设计展开成一份完整的字段手册。

A七种策略逐个拆透

A.1 固定长度 + Overlap

  • 机制：按 token 数（注意：用 embedding 模型自己的 tokenizer 计数，不是字符数——中文 1 字 ≈ 1-2 token，按字符切会严重超长）硬切；相邻块重叠 10-20%。
  • overlap 的真实作用与代价：作用是保证"恰好跨在切点上的句子/事实"至少完整出现在某一个块里。代价是（1）存储与 embedding 成本 ×(1+overlap%)；（2）检索时同一内容的两个重叠块可能同时进 top-k，挤占名额——所以生产中常配"近重复去除"（对 top-k 内两两相似度 > 0.95 的块去重，或用 MMR 采样）。
  • 何时用：日志、聊天记录、字幕这类真的没有结构的流水文本；或作为 baseline 对照组。

A.2 递归分割（RecursiveCharacterTextSplitter）

  • 机制细节：给定分隔符优先级列表（默认 ["\n\n", "\n", " ", ""]），先用最高优先级切；某段仍超长，就对该段降级用下一分隔符继续切；然后自底向上把碎片贪心合并到不超过 chunk_size。本质是"尽量在最大的自然边界断开"。
  • 中文必改项：默认分隔符没有中文句读，长段中文会直接跌到按空格/字符切。要传 ["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]。这是中文 RAG 最常见的低级失分点。
  • 失败模式：它只看字符不看语义——Markdown 的代码块中的空行、表格行之间的换行，都会被当成段落边界切碎。所以它的正确定位是"结构感知分块内部的兜底器"：先按结构切大块，超长的再交给它。

A.3 结构感知分块（Structure-Aware）

  • 机制：消费解析层输出的结构树（见解析深潜），按逻辑单元切：Markdown 按标题层级；代码按 AST 的函数/类边界（tree-sitter，LangChain 的语言感知 splitter 即基于此）；法律合同按条款编号；表格整表保留或按行组切且每块重复表头。
  • 两条铁律：（1）标题路径要拼进 chunk 文本参与 embedding（"年度报告 > 第三章 财务 > 3.2 营收\n..."），否则"营收增长 3%"这种块脱离章节语境完全无法被正确检索——这其实是 Contextual Retrieval 的零成本简化版；（2）宁可块大小不均匀，也不要跨结构边界合并（把 3.2 节结尾和 3.3 节开头拼进同一块，会制造语义杂交的劣质向量）。
  • 何时用：只要文档有结构就应该用。它是生产系统的默认正确答案，A.2 只做它的下游兜底。

A.4 语义分块（Semantic Chunking）

  • 机制细节：① 按句切分 → ② 对每句（或滑动窗口内几句拼接，抗单句噪声）做 embedding → ③ 计算相邻窗口余弦距离序列 → ④ 在距离超过阈值处（常用分位数法，如取距离分布的 95 分位）设为断点。直觉：话题切换处相邻句相似度骤降。
  • 诚实的评价：学术对比（如 Chroma Research 2024 的分块评测、Vectara 等的实验）反复发现语义分块相对结构感知分块的增益不稳定，而成本（全库逐句 embedding）确定很高。根因：好文档的作者已经用段落和标题把语义边界标出来了，语义分块是在用模型重新发现作者已经告诉你的信息。
  • 何时用：仅当文本真的没有可用结构（转录稿、OCR 后丢失格式的旧档案）时才轮到它。

A.5 Parent-Child / Small-to-Big

  • 机制细节：子块（128-256 token，甚至单句）做 embedding 入向量库；父块（其所属段落/小节，512-2048 token）存文档库（KV store）。检索命中子块 → 通过 parent_id 取回父块进 prompt。多个子块命中同一父块时去重，只取一次父块。LangChain ParentDocumentRetriever / LlamaIndex 句子窗口检索（命中句 ± N 句）是现成实现。
  • 为什么有效（值得背下来的解释）：单向量的语义分辨率有限，块越小向量越"纯"、检索越准；但 LLM 需要语境。Parent-child 把"用什么检索"和"给 LLM 看什么"解耦成两个独立可调的自由度——这是它优雅的根本原因。
  • 变体：还可以给同一父块建多路子表示——子块 + LLM 生成的该块摘要 + LLM 生成的"该块可回答的假想问题"（HyDE 的镜像，query-question 对称匹配往往比 query-passage 更准），全部指回同一父块。LangChain MultiVectorRetriever 即此。
  • 代价:需要维护两个存储 + 映射一致性（父块更新时所有子向量要同步重建）。

A.6 Contextual Retrieval（Anthropic, 2024-09）

  • 机制细节：索引时，对每个 chunk 调一次 LLM，输入 = 整篇文档 + 该 chunk，输出 = 50-100 token 的语境说明（"本块出自 ACME 公司 2023 年 Q2 SEC 文件，讨论其营收环比变化"），前置拼接后再做 embedding 和 BM25 索引（两路都要加语境，BM25 同样受益）。
  • 成本工程：每 chunk 一次 LLM 调用看似昂贵，但"整篇文档"这个前缀对同一文档的所有 chunk 是相同的 → 用 prompt caching 后文档前缀只计一次完整费用，Anthropic 给出的参考成本约 $1.02 / 百万文档 token。
  • 官方消融数据（检索失败率相对下降）：contextual embedding 单独 -35%；+ contextual BM25 -49%；再 + rerank -67%。这组数字值得记住，面试引用很有说服力。
  • 与 A.3 的关系：标题路径拼接是它的"免费 80% 版"；当文档结构差、或语境无法从标题推出（如对话记录、邮件线程）时，才值得上完整 LLM 版。

A.7 Late Chunking（Jina, 2024）

  • 机制细节（用你的 Transformer 知识精确理解）：常规做法是 先切块、每块独立过 encoder——块内 token 的注意力被截断在块边界，代词"它"永远看不到上文的指代对象。Late chunking 反转顺序：整篇文档（≤8192 token）一次过长上下文 embedding 模型 → 得到全文注意力语境下的每 token 隐状态 → 再按块边界对 token 向量做 mean pooling。每个块向量因此"免费"携带全文语境。
  • 与 Contextual Retrieval 的精确对比：两者动机完全相同（块脱离上下文导致语义残缺），实现哲学相反——CR 把语境显式写成文字（可读、可加进 BM25、但要付 LLM 费），LC 把语境隐式编码进向量（零额外调用、但 BM25 无法受益、且受 embedding 模型最大长度限制）。
  • 要求：必须用支持长上下文且验证过 late chunking 的模型（jina-embeddings-v3 等）；超过 8k 的文档要先做粗粒度切分（long late chunking）。
决策总图

实践排序：结构感知（含标题路径拼接）为地基 → 叠加 parent-child 解耦检索/生成粒度 → 语境缺失仍严重时按预算选 Contextual Retrieval（有钱、要 BM25 增益）或 Late Chunking（省钱、纯向量路线）。语义分块只服务无结构文本；固定长度只做 baseline。记住主文档的三角矛盾（检索粒度 / 生成粒度 / 语义自足性），每种策略不过是三角上的不同取舍点。

B为什么"停在 2024"？以及 2025 之后的真实前沿

B.1 先回答你的疑问：2024 不是知识过时，而是拐点本身

主文档表格截到 2024 有一个客观原因：Contextual Retrieval 和 Late Chunking（均为 2024）恰好是"分块作为独立研究问题"的收官之作。它们把"块该带多少上下文"这个最后的大问题给出了两个工程上够用的答案。此后领域的演化方向发生了转移——不是"发明更聪明的切法"，而是以下四条线：

B.2 前沿方向一：分块被上游"吸收"——解析层直接产出逻辑块

随着 Docling / MinerU 等版面理解管线成熟（见解析深潜），文档进入分块环节时已经是"标题树 + 元素类型"的结构化表示，分块退化为"在结构树上按 token 预算做装箱"的确定性算法（Docling 的 HybridChunker、各家 chunk-by-layout 功能）。行业共识正在变成：分块的质量问题，本质是解析的质量问题。这就是为什么 2025 年后你很少看到"新分块算法"论文，却大量看到文档解析模型的发布。

B.3 前沿方向二：分块被下游"吸收"——检索单元与生成单元彻底解耦

  • LLM 语境下的极端 small-to-big：检索单元做到命题级（Proposition-based Retrieval，Chen et al. 2023：把文本改写成一条条原子事实句"Dense X Retrieval"），生成单元给整节甚至整篇——长上下文模型让"父块"可以任意大，分块的生成侧约束基本消失。
  • 推理时动态选取：检索先命中粗粒度区域，再由模型在推理时决定实际读多少（LlamaIndex 的 auto-merging、各类"检索页码 → 现场读原文"的 agentic 读取工具）。块边界从"索引时固定"变成"查询时弹性"。

B.4 前沿方向三：Agentic / 查询时检索范式弱化预分块

  • Claude Code、Deep Research 类系统展示了另一条路：不建向量索引，用 grep/关键词/文件树导航 + LLM 现场读文件的 agentic 检索。当语料是代码库或结构良好的文件系统时，这条路的效果常常优于向量 RAG——因为它没有任何解析/分块损耗。你做智能体方向求职，这个对比一定要能讲（何时向量索引仍不可替代：海量非结构化语料、毫秒级延迟要求、模糊语义匹配）。
  • 记忆型/持续摄入型系统（mem0、各家 memory 产品）用"抽取式写入"（LLM 把新信息蒸馏成原子事实/知识条目再入库）取代"切块式写入"——分块被"抽取"替代。

B.5 前沿方向四：多模态检索绕过分块

ColPali/ColQwen 路线（主文档 §11）把页面作为检索单元、patch 作为匹配单元，解析和分块整条链路被跳过。2025 年以来该家族持续演进（更强 VLM 底座、更省存储的池化方案），在视觉密集文档上已是严肃的生产选项。"最好的分块是不分块"在这条线上被字面实现。

给你的判断框架

面试被问"分块最新进展"时的高分答法：先讲 2024 的两个收官方案（CR / Late Chunking）及其背后的共同矛盾，再指出领域重心已从"怎么切"迁移到"上游解析结构化、下游粒度解耦、agentic 现场读取、多模态免切分"四条线——这展示的是趋势判断力，比背新名词值钱得多。

CMetadata 完全手册

Metadata 是 chunk 的"户口本"。它的设计质量决定了四件事的上限：过滤检索、权限、溯源、索引运维。而且它必须在入库时一次打对——上线后补字段 = 全量重建。

C.1 字段分类：四种用途，四种命运

类别典型字段用途与去向
1. 检索增强型
（参与 embedding）		title_path（标题面包屑）、doc_title、section_summary拼进 chunk 文本一起 embedding，直接改变向量语义。这是唯一"进向量"的一类，也是最容易被忽略的免费增益（见 A.3 铁律一）
2. 过滤型
（结构化查询条件）		doc_type、department、product_line、language、updated_at、effective_date、status(active/deprecated)存为向量库 payload，检索时做 filter。是 self-query（主文档 §8）和时效消解的物质基础。字段取值必须是受控枚举（"hr" 不能一会儿写 "HR" 一会儿写 "人力"），否则过滤形同虚设
3. 安全型acl_groups、tenant_id、classification(public/internal/confidential)检索层强制过滤（用户组 ∩ acl_groups ≠ ∅），绝不进 prompt 靠模型自觉。多租户 SaaS 中 tenant_id 过滤是数据不串号的生命线，通常配合 collection 物理隔离双保险
4. 运维/溯源型doc_id、chunk_id、parent_id、source_uri、page_no、bbox、content_hash、ingest_version、embedding_model不参与检索。支撑：按 doc_id 级联删除（防僵尸块）、hash 增量更新、引用跳转原文页码/高亮、"这批向量是哪个管线版本产的"事故追查

C.2 一个生产级 schema 示例（逐字段注释）

{
  // ---- 1. 检索增强（拼进文本参与 embedding）----
  "title_path": "员工手册 > 假期制度 > 年假",

  // ---- 2. 过滤（受控枚举 + 规范化格式）----
  "doc_type": "policy",              // 枚举: policy|faq|report|contract|code
  "department": "hr",                // 枚举，入库时校验
  "language": "zh",
  "updated_at": 1774137600,          // 注意！存 unix 时间戳而非字符串——
                                     // 多数向量库只支持数值范围过滤，"2026-03-01" 字符串没法做 >= 查询
  "status": "active",               // active|deprecated，废止文档默认过滤，防"引用旧政策"事故

  // ---- 3. 安全 ----
  "tenant_id": "acme",
  "acl_groups": ["hr", "managers"],

  // ---- 4. 运维 / 溯源 ----
  "doc_id": "handbook-2026",         // 级联删除/更新的键
  "chunk_id": "handbook-2026#014",
  "parent_id": "handbook-2026#sec-3.2",  // parent-child 映射
  "source_uri": "confluence://SPACE/pages/1234",
  "page_no": 12,                     // + bbox → 前端引用高亮
  "content_hash": "sha256:9f2c…",   // 增量更新：hash 未变则跳过重嵌
  "ingest_version": "pipeline-v3",   // 管线版本，事故归因用
  "embedding_model": "bge-m3@q1"     // 防止混模型向量共存的静默灾难
}

C.3 Metadata 从哪来：三个来源

  1. 解析层自动产出：title_path、page_no、bbox、元素类型——这是解析要输出结构化 JSON 而不只是纯文本的原因（见解析深潜 §B.6）。
  2. 源系统携带：Confluence/SharePoint/数据库自带的作者、部门、权限、更新时间——connector 摄入时映射，权限字段必须从源系统同步，且要处理源端权限变更的增量同步（用户被移出用户组后，多久在 RAG 里生效？这是安全审计必问题）。
  3. LLM 抽取补全：源信息缺失时，用 LLM 从内容推断 doc_type、主题标签、涉及产品线等。注意抽取结果要落在受控枚举上（structured output + 枚举校验），并接受它有错误率——过滤型字段错误会导致该 chunk 永久检索不到，比不打标更糟，所以低置信度时宁可留空。
Metadata 高频事故清单
  • 日期存成字符串 → 无法范围过滤（见上方注释），self-query 静默失效。
  • 枚举值不受控（大小写/中英文混用）→ 过滤命中率诡异波动。
  • 过滤条件过严 + 向量库 filtered-ANN 实现差 → 召回率断崖（主文档 §5.2 的图连通性问题）。排查时先去掉 filter 对照。
  • ACL 只打在文档级、chunk 继承逻辑有 bug → 单块越权泄露。ACL 必须落到每个 chunk 的 payload 上并写测试。
  • 需要新过滤字段但当初没打 → 只能全量重跑摄入管线。所以 schema 设计时把"未来 6 个月可能的过滤需求"预留出来，宁多勿少（多余字段的成本几乎为零，缺字段的成本是一次全量重建）。
