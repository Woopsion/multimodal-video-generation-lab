文档解析：工业级全流程详解

"解析"听起来像脏活，但它是 RAG 中错误不可恢复的环节——分块可以重切、embedding 可以重算， 解析丢掉的结构信息永远回不来。本文给出工业成熟方案的完整流水线、工具选型矩阵、以及一个可跑的端到端例子。

A为什么解析这么难：PDF 的本质

理解了 PDF 格式的本质，你就理解了所有解析工具在对抗什么。

PDF 不是文档格式，是打印指令格式。它的内部内容大致是这样的绘图指令流：

BT /F1 12 Tf  72 700 Td  (第三季) Tj  ET     ← "在坐标(72,700)用12号字画出'第三季'"
BT /F1 12 Tf  110 700 Td (度营收) Tj  ET     ← 下一段文字，坐标独立

它没有"段落""标题""表格"的概念，只有带坐标的文字碎片和线条。所以解析 PDF 本质上是一个逆向工程问题：从二维排版结果反推出一维逻辑结构。由此派生出全部经典病灶：

  • 阅读顺序：双栏论文按 y 坐标扫描会左右两栏串行（"本文提出了在图3中可以看到一种新方法……"）。
  • 表格：PDF 里的表格 = 一堆线条 + 一堆按坐标摆放的文字，"哪些字属于哪个单元格"需要几何推断；合并单元格、跨页表格、无边框表格逐级加难。
  • 页眉页脚/页码：每页重复的噪声文本，混进 chunk 会污染检索（一个 chunk 里出现"第 12 页 机密 内部资料"）。
  • 公式/特殊符号：字体子集化后字符映射可能损坏，抽出来是乱码。
  • 扫描件：根本没有文字层，纯图片，必须 OCR。
  • 跨页断裂：一个段落/表格被分页截断，朴素的按页解析会把它切成两个不完整片段。
认知升级

所以现代解析方案的共同思路是：不要试图从指令流"读"出结构，而是像人一样"看"出结构——把页面当图像，用视觉模型做版面分析（Layout Analysis）。这也解释了为什么解析技术近两年突然变好：它搭上了视觉深度学习的便车。你的 ViT/CLIP 背景在这里又一次可以直接迁移。

B工业级解析流水线的标准解剖

MinerU、Docling、marker、商用 Document AI 的内部结构高度趋同，都是下面这条流水线的变体。逐段拆解：

1 文档分诊→ 2 版面检测→ 3 阅读顺序恢复→ 4 分类型内容抽取→ 5 跨页缝合→ 6 输出结构化 Markdown/JSON

B.1 文档分诊（Triage）

第一步判断文档类型，路由到不同处理路径——这一步常被自研管线遗漏，是很多线上事故的根源：

  • 原生 PDF（有文字层）：走"文字层抽取 + 版面模型辅助"的快速路径，文字 100% 准确。判断方法：抽样几页看能否提取到合理文本。
  • 扫描件 / 图片型 PDF：走 OCR 路径。注意混合文档（前 10 页原生、后面是扫描附件）要按页分诊。
  • Office 文档（docx/pptx/xlsx）：是 XML 压缩包，结构是显式的，永远不要把它们转成 PDF 再解析——那是把结构化数据先降级成打印指令再逆向，纯属自残。直接用 python-docx / Docling 原生读取。
  • HTML / Markdown：结构现成，清洗掉导航/广告即可（trafilatura 做网页正文抽取很成熟）。

B.2 版面检测（Layout Detection）

把每页渲染成图像，用目标检测模型（YOLO 系或 DETR 系，在 DocLayNet / PubLayNet 等标注数据集上训练）把页面切成带类别的区块：

[
  {"type": "title",   "bbox": [72, 60, 540, 95],  "conf": 0.98},
  {"type": "text",    "bbox": [72, 110, 300, 400], "conf": 0.95},  ← 左栏
  {"type": "text",    "bbox": [310, 110, 540, 400],"conf": 0.94},  ← 右栏
  {"type": "table",   "bbox": [72, 420, 540, 600], "conf": 0.97},
  {"type": "figure",  "bbox": [...]}, {"type": "formula", "bbox": [...]},
  {"type": "page_footer", "bbox": [...]}   ← 直接丢弃或入 metadata
]

典型类别集：标题/正文/列表/表格/图片/图题/公式/页眉/页脚/脚注。这一步解决了"页眉页脚污染"和"图文混排"问题。

B.3 阅读顺序恢复（Reading Order）

对检测出的区块排序。简单版面用几何规则（XY-Cut 递归切分：先找垂直空白带分栏、再按 y 排序）；复杂版面（杂志、报纸、试卷）用专门的阅读顺序模型（如 LayoutReader，把区块序列排序当作序列预测任务）。双栏串行问题在这一步被根治。

B.4 分类型内容抽取

  • 正文区块：原生 PDF 直接按 bbox 裁取文字层（准确且免费）；扫描件送 OCR（PaddleOCR / 商用 OCR）。
  • 表格区块：送专门的表格结构识别模型（TSR，如 TableMaster、Docling 的 TableFormer）：先识别行列网格与合并单元格，再填充文字 → 输出 HTML/Markdown 表格。表格是独立子问题，用通用 OCR 硬抽注定失败。
  • 公式区块：公式识别模型转 LaTeX（如 UniMERNet / pix2tex）。
  • 图片区块：裁图保存，记录 bbox 与图题关联；可选调 VLM 生成描述（衔接主文档 §11 多模态路线 A）。

B.5 跨页缝合与 B.6 结构化输出

  • 缝合：段落末页无句号 + 下页首无缩进 → 合并；表格跨页 → 按表头对齐拼接。
  • 输出统一为带层级的 Markdown + 结构 JSON（每个元素保留 type / 页码 / bbox / 标题层级），供下游结构感知分块直接消费。保留 bbox 的价值：前端可以做"点击引用高亮原文位置"的溯源体验。

选型决策树
  • 文档简单（纯文字、单栏）→ PyMuPDF 快速路径，别过度工程。
  • 自建、文档含表格/多栏 → Docling（通用）或 MinerU（学术/中文文献）。
  • 来源极杂、要一个接口通吃 → unstructured。
  • 预算充足求稳 → 商用 API。
  • 无论选哪个：VLM 兜底失败页 + 人工抽检机制都值得配。

D端到端可跑示例：Docling 版

# uv add docling
from docling.document_converter import DocumentConverter
from docling.chunking import HybridChunker

converter = DocumentConverter()          # 内部自动完成：分诊→版面检测→表格识别→阅读顺序→缝合
result = converter.convert("annual_report.pdf")
doc = result.document                    # DoclingDocument：带层级结构的统一中间表示

# 路线1：导出 Markdown（表格已是管道表格，标题带层级）人工抽检解析质量
md = doc.export_to_markdown()

# 路线2：直接结构感知分块（尊重标题/表格边界，chunk 自带标题路径元数据）
chunker = HybridChunker(tokenizer="BAAI/bge-m3", max_tokens=512, merge_peers=True)
for chunk in chunker.chunk(doc):
    text = chunker.contextualize(chunk)  # 关键：自动把 "文档名 > 章 > 节" 标题路径拼进 chunk 文本再去 embedding
    meta = {
        "headings": chunk.meta.headings,             # ['年度报告', '第三章 财务', '3.2 营收']
        "page": chunk.meta.doc_items[0].prov[0].page_no,  # 页码 → 支持引用溯源
    }
    vectorstore.add_texts([text], metadatas=[meta])
上线前必做的质量验证
  • 解析也需要评估集：抽 20-50 页有代表性的页面（含最难的表格/双栏页），人工核对解析输出，统计表格单元格错误率、阅读顺序错误率。解析质量不达标，后面全部白搭。
  • 对数字敏感场景（财报、医疗），VLM/OCR 路线要加"抽取数字与原文交叉核对"的校验，防静默篡改。
  • 监控解析失败率与异常页（空文本、乱码比例超标自动告警 + 转人工/VLM 兜底队列）。
