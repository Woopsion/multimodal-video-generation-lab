RAG 原始论文彻底讲透：
两个变体、边际化公式、与"冻结管道"

目标：读完本文，你能不看任何资料，用自己的话向面试官讲清楚—— ① 那两个公式每个符号在算什么；② RAG-Sequence 和 RAG-Token 的区别（并配一个数值例子）； ③ "冻结组件的管道拼接"到底冻结了什么、为什么工业界选了这条路。 文末附口头表达模板。

A预备概念一：隐变量与边际化（公式里的 Σ 从哪来）

公式抽象的根源通常是预备概念没打牢。先把"边际化"用一个和 RAG 无关的例子讲到不能再具体。

A.1 从一个生活例子开始

问：明天你迟到的概率是多少？这取决于你走哪条路（隐变量 z）：

P(迟到) = P(走大路)·P(迟到|走大路) + P(走小路)·P(迟到|走小路) = 0.7 · 0.1 + 0.3 · 0.4 = 0.19

这就是全概率公式。你不知道明天到底走哪条路，所以把所有可能的路"加权求和"掉——这个"把不确定的中间变量求和消掉"的动作，就叫边际化（marginalization）；那个不被直接观测、但影响结果的中间变量（走哪条路），就叫隐变量（latent variable）。

A.2 翻译到 RAG

RAG 论文的世界观：要回答问题 x，生成答案 y，中间隔着一个"看了哪篇文档 z"。训练数据里只有 (x, y) 对，没人标注"标准答案是看哪篇文档写出来的"——所以 z 是隐变量，只能边际化掉：

p(y | x) = Σ_z p(z | x) · p(y | x, z) ──────── ───────── 检索器： 生成器： "看这篇文档 "看着这篇文档， 的概率" 写出这个答案的概率"

逐个拆解两个部件：

  • p(z|x)，检索器：就是 DPR 双塔。对 query 向量和每篇文档向量做内积，再对 top-k 篇的内积分数做 softmax，得到一个归一化的"文档权重分布"。例如 k=2 时可能是 {z₁: 0.6, z₂: 0.4}。（严格数学上 Σ 应遍历全库几百万篇，工程上近似为只对 ANN 取回的 top-k 求和——这个近似的合理性在REALM 深潜讲过。）
  • p(y|x,z)，生成器：BART。输入 = 文档 z 拼上问题 x，输出 = 生成答案 y 的概率。
为什么非要"边际化"而不是"取 top-1"？

如果只取最相关的 1 篇文档（argmax 而非求和），检索这一步就变成了不可导的硬选择，梯度无法告诉检索器"你选的文档好不好"。 换成加权求和后，每篇文档都以"软权重"参与最终概率——某篇文档帮助了生成，梯度就会流过它的权重 p(z|x)，把这篇文档的向量拉近 query。Σ 的存在就是为了让"检索"这个离散动作变得可导、可训练。这和你熟悉的 attention 用 softmax 替代硬选择是同一个思想。

B预备概念二：自回归分解（公式里的 Π 从哪来）

这个你其实已经会了，只是要把它和上面的 Σ 区分开。语言模型生成一句话的概率，按链式法则逐 token 分解：

p(y | x, z) = Π_{i=1..N} p(y_i | x, z, y_{<i}) 例：y = "巴黎 很 美" p("巴黎 很 美") = p("巴黎") × p("很"|"巴黎") × p("美"|"巴黎 很")

所以现在我们手里有两个运算：

  • Σ（对文档求和）——消掉"看哪篇文档"的不确定性；
  • Π（对 token 连乘）——把整句概率分解为逐词概率。

RAG-Sequence 和 RAG-Token 的全部区别，就是这两个运算谁套在外面。就这么简单。下面展开。

C两个变体：Σ 和 Π 的嵌套顺序之争

C.1 RAG-Sequence：Σ 在外 —— "先选书，再写完整本答案"

p(y|x) = Σ_z p(z|x) · [ Π_i p(y_i | x, z, y_{<i}) ] ↑外层：对文档求和 ↑内层：在“同一篇文档”下写完整个答案

比喻：图书馆里有 k 本候选书。你选定一本书，从头到尾照着它写完整个答案；对每本书都这么做一遍，得到 k 个"(这本书的权重) × (照这本书写出该答案的概率)"，加起来。整个答案自始至终只忠于一篇文档，"换文档"只发生在完整答案之间，不发生在答案内部。

C.2 RAG-Token：Π 在外 —— "每写一个词，全体文档投一次票"

p(y|x) = Π_i [ Σ_z p(z|x) · p(y_i | x, z, y_{<i}) ] ↑外层：逐 token 连乘 ↑内层：“这一个词”由 k 篇文档加权投票决定

比喻：k 位专家（每人只读过一篇文档）组成委员会。每生成一个词，就开一次投票：每位专家给出自己心目中下一个词的概率分布，按文档权重 p(z|x) 加权平均成一个混合分布，从中出词；然后带着已生成的词，进行下一轮投票。于是答案的不同部分可以事实上依赖不同的文档——写前半句时文档 A 的专家话语权大（因为它对这个词概率高），写后半句时文档 B 的专家接管。

注意一个容易误解的细节：投票权重 p(z|x) 在整个生成过程中是固定的（由 query 一次算出，不随已生成内容更新）。变化的是各文档下的 token 分布 p(y_i|x,z,y<i)，"接管"是通过它实现的。

C.3 数值算例：亲手算一遍，抽象感即刻消失

设问题 x = "法国和德国的首都分别是？"，理想答案 y = [巴黎, 柏林]（简化为 2 个 token）。检索回 2 篇文档，权重各 0.5：

  • z₁ = 一篇只讲法国的文档：在它条件下 p(巴黎)=0.9，p(柏林|巴黎)=0.1（文档里没有德国信息，只能瞎猜）
  • z₂ = 一篇只讲德国的文档：p(巴黎)=0.1，p(柏林|巴黎)=0.9

RAG-Sequence（先在单篇文档下写完，再加权）：

照 z₁ 写全句: 0.9 × 0.1 = 0.09 ← 后半句没依据，概率被拖垮 照 z₂ 写全句: 0.1 × 0.9 = 0.09 ← 前半句没依据，同样被拖垮 p(y|x) = 0.5×0.09 + 0.5×0.09 = 0.09

RAG-Token（每个 token 先混合，再连乘）：

token₁ "巴黎": 0.5×0.9 + 0.5×0.1 = 0.5 ← z₁ 的专家扛起了这个词 token₂ "柏林": 0.5×0.1 + 0.5×0.9 = 0.5 ← z₂ 的专家扛起了这个词 p(y|x) = 0.5 × 0.5 = 0.25
算例揭示的本质

同样的检索结果、同样的生成器，正确答案在 RAG-Token 下概率 0.25，在 RAG-Sequence 下只有 0.09。 因为这个答案需要拼合两篇文档的信息：Sequence 强迫"从一而终"，任何单篇文档都写不好全句；Token 允许"逐词换靠山"。 反过来，若答案只需一篇文档（绝大多数简单事实问答），Sequence 的"专一"反而是优点——不会被无关文档的噪声分布稀释。论文实验里两者互有胜负，正是这个原因。

C.4 解码：为什么 Sequence 生成起来很别扭（选读，面试加分细节）

  • RAG-Token 可以直接用标准 beam search：因为每一步的"下一词分布"就是那个混合分布，算出来即可正常解码——它本质上就是一个（每步做 k 次前向再加权的）普通语言模型。
  • RAG-Sequence 不行：它的整句概率是"先各自写完再求和"，逐步解码时你无法知道一个前缀在"求和后"的概率。论文的做法：对每篇文档各跑一次独立 beam search，把所有文档产出的候选句汇总成集合，再为每个候选句在每篇文档下补算 p(y|x,z)（候选句没出现在某文档的 beam 里就要额外跑前向，称 Thorough Decoding；嫌贵可近似记 0，称 Fast Decoding），最后按公式加权排序选优。——记住直觉即可：Token 是"一个混合模型正常解码"，Sequence 是"k 个模型各自解码后离线合并计票"。

C.5 训练：梯度到底流去了哪

训练目标就是最大化上面边际概率的对数（最小化 -log p(y|x)），端到端反传：

  • 流向生成器（BART 全参数）：学会"看着文档写答案"。
  • 流向query encoder（通过 p(z|x) 中的 softmax）：有用的文档权重被推高 → query 向量被拉向有用文档。
  • 文档 encoder 被冻结！这是一个精彩且常被忽略的细节：如果文档向量也更新，几百万篇的 ANN 索引就得随训练反复重建（REALM 踩过的坑）。RAG 论文的取舍：文档塔用 DPR 预训练权重定死，只训 query 塔——可见"冻结"不是后来工业界的堕落，原始论文自己就冻了一半。

D什么叫"冻结组件的管道拼接"

这个短语描述的是今天工程界 RAG 与 2020 论文 RAG 的根本差异。逐词拆解。

D.1 逐词拆解

  • 组件：embedding 模型（如 BGE）、向量库、LLM（如 GPT-4o / Qwen）。
  • 冻结（frozen）：指参数不再更新。BGE 是智源训练好的，你只做推理；GPT-4o 是 API，你连权重都摸不到。你的 RAG 系统运行一万次，这些模型的参数一个比特都不会变。
  • 管道拼接（pipeline）：组件之间的"接口"不是梯度、不是概率，而是一段文本——检索结果被粘贴进 prompt。信息只单向流动：检索器 → 文本 → LLM，没有任何信号从 LLM 反向流回检索器。

D.2 与论文 RAG 的正面对比

维度论文 RAG（2020，联合训练）工程 RAG（今天，冻结管道）
数学形式p(y|x) = Σ_z p(z|x)·p(y|x,z)
对 k 篇文档各跑一次生成再按概率加权		p(y | x ⊕ z₁ ⊕ z₂ ⊕ … ⊕ z_k)
k 篇文档全部拼进一个 prompt，跑一次生成。没有 Σ，没有边际化——"融合"发生在 LLM 内部的 attention 里
检索分数 p(z|x) 的用途参与最终概率计算，接收梯度只用来排序取 top-k，之后被丢弃
组件间接口可导的概率图字符串拼接
检索器如何知道自己检索得好不好梯度直接告诉它永远不知道——这是冻结管道的根本缺陷
改进手段继续训练换模型、改 prompt、加 rerank、调分块（全是"外科手术"，不动参数）

D.3 为什么工业界选了"更笨"的路线？

四个现实原因，每个都足够硬：

  1. LLM 是黑盒：主力生成模型是闭源 API，拿不到梯度和 logits，联合训练在物理上不可能。
  2. stale index 工程噩梦：联合训练检索器 = 文档向量持续漂移 = 亿级索引反复重建（REALM 的老问题，规模放大一万倍）。
  3. 模块化红利：冻结组件可独立升级——明天出了更强的 embedding 模型，换掉重建索引即可，LLM 不用动；反之亦然。联合训练则把所有组件焊死成一个整体。
  4. 够用：现代 LLM 的 in-context 能力足够强，"把资料贴进 prompt"这个粗糙接口的损失，多数场景可以接受。

D.4 缺陷与"部分解冻"的补救谱系

冻结管道的根本病：检索器优化的目标（向量相似）≠ 生成器需要的目标（对回答有用）。两者常常错位——"语义最像 query 的段落"未必是"最能支撑答案的段落"。业界的补救按"解冻程度"排成一个谱系：

方案思路解冻了什么
Rerank（主文档 §7）加一个 cross-encoder 重排，用更准的相关性代理弥合错位什么都不解冻，加组件
REPLUG（Shi et al. 2023）把黑盒 LLM 当"打分器"：哪篇文档拼进去能让正确答案的困惑度更低，就训练检索器把该文档的检索分布向这个"效用分布"对齐（KL 散度）。LLM 全程冻结，只训检索器——巧妙绕过黑盒限制，是 REALM 思想在 API 时代的复活只解冻检索器
RA-DIT（Meta 2023）双向微调：LLM 学会更好地利用检索内容 + 检索器向 LLM 偏好对齐，交替进行两边都解冻（需开源 LLM）
Self-RAG（主文档 §9.2）不训检索器，转而训 LLM 输出反思 token 自己判断"检索结果好不好、要不要重检"把"质量判断"从梯度搬到推理时控制流
一个统一视角（面试杀手锏）

主文档 §10 的 Agentic RAG（检索→评分→改写→重试循环）可以理解为：联合训练想在"训练时"用梯度解决的检索-生成对齐问题，Agentic RAG 改在"推理时"用控制流解决——grader 节点扮演了损失函数的角色，改写重试扮演了梯度更新的角色。2020 到今天的技术史，就是这个对齐问题从参数空间迁移到控制流空间的历史。能讲出这句话，说明你真正打通了 RAG 的古今脉络。

E口头表达模板：把它"讲出来"

你说"讲不出来"，所以这里直接给出可复述的两档版本。先背骨架，再用自己的话填肉。

E.1 三十秒版（概念确认题）

"原始 RAG 论文把检索文档当作隐变量：不知道答案该依据哪篇文档，就对 top-k 篇按检索概率加权求和，这叫边际化。两个变体的区别在于求和的位置：RAG-Sequence 在整句层面求和——整个答案从头到尾只依据一篇文档写完，再对 k 篇的结果加权；RAG-Token 在每个词层面求和——每生成一个 token，k 篇文档各出一个分布加权混合，所以答案的不同部分可以依赖不同文档。需要拼合多篇文档信息的答案，Token 显著占优。"

E.2 两分钟版（深挖题，含冻结管道）

"……（先说三十秒版）……另外有三个值得展开的点。

第一，边际化的动机是可导性：如果硬选 top-1 文档，检索就是不可导的离散动作；换成 softmax 加权求和后，梯度能流回 query encoder——'哪篇文档对生成有帮助'自动定义了'什么叫检索得好'，不需要人工标注相关性。这和 attention 用 softmax 替代硬对齐是同一个思想。

第二，解码难度不对称：RAG-Token 每步的混合分布可以直接标准 beam search；RAG-Sequence 的整句求和没法逐步解码，要对每篇文档独立跑 beam search 再合并计票，论文里叫 Thorough/Fast Decoding。

第三，今天的工程 RAG 已经不是这个数学形式了：我们把 top-k 文档全部拼进一个 prompt、跑一次生成——没有边际化，融合发生在 attention 内部；检索分数只用于排序，之后就被丢弃；embedding 模型和 LLM 都是冻结的，组件间靠字符串拼接、没有梯度往来。这条'冻结管道'路线赢在模块化和对黑盒 API 的兼容，代价是检索器永远收不到'检索得好不好'的反馈——检索目标和生成需求会错位。所以才有 rerank 做补丁、REPLUG 用冻结 LLM 的困惑度反过来训检索器、以及 Agentic RAG 在推理时用'评分-改写-重试'的控制流来顶替当年梯度干的活。"
